### What Django does

Read at 5.2.19 and 6.1.3. Paths are relative to the `django` package; the cited code is the same in both unless noted.

1. **The registry knows which app holds a module.** `Apps.get_containing_app_config(object_name)` returns the innermost installed app whose `name` is a dotted prefix of the name, or `None` (`apps/registry.py`, line 251). 0021 Decision 5 already uses it for "inside the providing app". An app's models module is `<name>.models`, which `AppConfig.import_models` imports when the app has that submodule (`apps/config.py`, `MODELS_MODULE_NAME`).
2. **A model can be named by a string in several places.** `Apps.get_model` takes `"<label>.<Model>"` or a label and a model name (`apps/registry.py`, line 188; the split is at line 206); `AppConfig.get_model` takes a model name alone. `ModelSignal` resolves a `sender` given as a string through `_lazy_method` (`db/models/signals.py`, line 15). A relation field resolves a string through `resolve_relation` (`db/models/fields/related.py`, line 45 in 5.2.19, 52 in 6.1.3) and `Apps.lazy_model_operation`. `get_user_model()` reads `settings.AUTH_USER_MODEL` (`contrib/auth/__init__.py`, line 278 in 5.2.19, 261 in 6.1.3).
3. **A module can be loaded from a string.** `django.utils.module_loading.import_string` (line 19) and `django.urls.include`, which imports a string argument, or the first element of a tuple, at the call (`urls/conf.py`, line 17). `importlib.import_module` takes its package as a keyword or as the second positional argument; Django's own `migrate` writes `import_module(".management", app_config.name)` (`core/management/commands/migrate.py`, line 106 in 5.2.19, 107 in 6.1.3).
4. **Every management command runs every registered check, and on 6.1 that asks every alias's features.** `BaseCommand.execute` calls `self.check()` when `requires_system_checks` is set, which by default is `"__all__"` (`core/management/base.py`, line 270 and 459 in 5.2.19, 272 and 461 in 6.1.3); a check registered with `deploy=True` runs only under `check --deploy` (`core/checks/registry.py`). On 6.1.3, `run_checks` sets `databases = list(connections)` when it is given none; 5.2.19 passes `None`. The model field checks then ask each alias's features: `JSONField._check_supported` reads SQLite's `supports_json_field`, which opens a cursor (`db/backends/sqlite3/features.py`, line 164 in 6.1.3). Probe, by a reviewer of this record, with one `JSONField` model, a SQLite path that did not exist and a plain command run through `execute_from_command_line`: on 5.2.19 no connection opened and no file appeared; on 6.1.3 a connection to `default` opened and a 0-byte file appeared. With `databases=[]`, neither version asks an alias. The `check` command sets `requires_system_checks = []`, runs the checks itself, fails at `ERROR` by default (`--fail-level`, `core/management/commands/check.py`, line 36), and takes app labels and `--database`, of which Django's documentation says the database checks "will not be run" by default. Django's documentation asks check ids to follow `applabel.X001`, with the letter giving the level ([system checks](https://docs.djangoproject.com/en/5.2/topics/checks/)).
5. **One method opens every connection.** Every backend opens through `BaseDatabaseWrapper.connect` (`db/backends/base/base.py`, line 237), which calls the backend's `get_new_connection`; no backend shipped with Django overrides `connect` (sqlite3, postgresql, mysql and oracle override only `get_new_connection`). Django's own `SimpleTestCase` forbids connections by patching `BaseDatabaseWrapper.ensure_connection` for the length of a test class (`test/testcases.py`, `ensure_connection_patch_method`), raising `DatabaseOperationForbidden`, an undocumented `AssertionError` subclass in that module; the per-instance part of that guard moved to `connection.features.disallowed_simple_test_case_connection_methods` in 6.1.
6. **An app's package has one directory in Django's model.** `AppConfig._path_from_module` takes the directory of a package's `__file__` when its `__path__` does not hold exactly one entry, and refuses a package with no `__file__`, a namespace package, that has several filesystem locations, unless the config sets `path` (`apps/config.py`, line 71).
7. **`manage.py` loads apps before it looks up the command.** `ManagementUtility.execute` reads `settings.INSTALLED_APPS` and calls `django.setup()` before `fetch_command(subcommand)` (`core/management/__init__.py`). An exception raised while apps load, or while settings are read again in `fetch_command`, ends the process with a traceback before any command runs.

### What other boundary tools do

- **Packwerk** checks Ruby packages. `enforce_dependencies` is set per package in its `package.yml`, apart from its privacy rule. Existing violations are written by `update-todo` to a generated `package_todo.yml` per package, and its `strict` mode refuses new entries ([usage](https://github.com/Shopify/packwerk/blob/main/USAGE.md)). Shopify's [retrospective](https://shopify.engineering/a-packwerk-retrospective) reports that privacy checks "had transformed Packwerk into something it was never intended to be: an API design tool", producing "endless poorly-documented public code that was never meant to be public in the first place", and that they "were removed from Packwerk with the release of version 3.0"; of the todo files: "With every new feature added, these todo files grew larger." It also advises, when a violation is at the level of the graph, to "consider adjusting your package layout". Packwerk offers `cache` and `parallel` options.
- **ArchUnit**'s `FreezingArchRule` stores a rule's violations; "On consecutive runs only new violations will be reported", fixed ones are removed from the store, line numbers are ignored when matching, a store is created only when `allowStoreCreation` is set (default false), and updates are allowed by default ([user guide](https://www.archunit.org/userguide/html/000_Index.html)).
- **deptrac** writes a baseline with `--formatter=baseline` and turns on a GitHub Actions formatter by itself in that CI, beside JUnit and Code Climate ([formatters](https://deptrac.github.io/deptrac/formatters/)). **ESLint**'s bulk suppressions write `eslint-suppressions.json` with `--suppress-all` and report unused entries until `--prune-suppressions` ([suppressions](https://eslint.org/docs/latest/use/suppressions)).
- **Tach** keeps modules, their `depends_on`, an `exact` mode for unused declared dependencies, a per-module `unchecked` flag and `forbid_circular_dependencies` in `tach.toml` ([configuration](https://docs.gauge.sh/usage/configuration)). **Spring Modulith**'s `verify()` requires that "the dependencies between modules have to form a directed acyclic graph", and a module may list `allowedDependencies` or be marked open in its own code ([verification](https://docs.spring.io/spring-modulith/reference/verification.html), [fundamentals](https://docs.spring.io/spring-modulith/reference/fundamentals.html)). **Nx**'s `enforce-module-boundaries` checks dependencies by tag (`depConstraints`) and reports circular dependencies ([guide](https://nx.dev/docs/technologies/eslint/eslint-plugin/guides/enforce-module-boundaries)).

Across them, enforcement posture lives in a repository file that does not vary by environment, and the rule on what may be depended on is kept apart from the rule on what is public.

### What the candidate engines are

Read from their wheels, installed in a throwaway virtual environment on Python 3.13 and removed afterwards. import-linter 2.17 was released on 2026-11-18, after the trial; per its PyPI metadata it raises its floors to `click>=8.2.0` and `grimp>=3.20`. The comparisons below rest on the wheels that were read.

- **import-linter 2.16** (BSD 2-Clause; released 2026-11-06, after 2.11 to 2.15 between March and September 2026; ships `py.typed`; Python 3.11 or newer; classified free-threading stable). It depends on `click>=7`, `grimp>=3.19` and `rich>=14.2.0`; the trial install also brought `markdown-it-py`, `mdurl` and `Pygments`. Its public Python API is `lint_imports(config_filename=...)` and `read_configuration(config_filename)` (`importlinter/application/use_cases.py`, `importlinter/api.py`): contracts come from an INI or TOML file, custom contract types are named in that file, and the report is rendered with `rich`. `create_report(user_options)` takes options in code, from the `importlinter.application` package, outside the documented API. Its contract types are `forbidden`, `independence`, `layers`, `acyclic_siblings` and `protected`; `protected` checks that a set of modules is "only directly imported by" a set of allowed importers (`importlinter/contracts/protected.py`).
- **grimp 3.19** (BSD 2-Clause; 3.19 released 2026-11-06 and 3.20 on 2026-11-13; no dependencies; `py.typed`; classified CPython only). Its scanner is a Rust extension, `grimp/_rustgrimp`, shipped as one wheel per CPython minor version, `cp311` to `cp315`, `cp314t` and `cp315t`, for Linux x86-64, aarch64 and others, macOS and Windows. It shipped CPython 3.14 wheels on 2025-10-09 (3.12) and 3.15 wheels from 2026-07-03 (3.15). `build_graph(..., cache_dir=...)` writes a cache to `.grimp_cache` in the working directory unless `cache_dir=None` (`grimp/adaptors/caching.py`, `DEFAULT_CACHE_DIR`; `grimp/application/usecases.py`). Its graph is documented API: `find_modules_directly_imported_by`, `get_import_details` with line numbers, `find_shortest_chains`.
- **Tach 0.35.3** (MIT; released 2026-10-06; Rust wheels). It depends on `pyyaml`, `tomli-w`, `rich`, `prompt-toolkit`, `gitpython`, `networkx` and `pydot`. Its modules, their allowed dependencies and their interfaces are written in a `tach.toml`.
- **Python's own parser.** `ast`, `importlib.util.resolve_name` and `tomllib` are in the standard library of every supported Python (0012's floor is 3.12; `tomllib` arrived in 3.11). The check uses `ast.Import`, `ast.ImportFrom`, `ast.Call`, `ast.keyword`, `ast.Subscript`, `ast.Attribute`, `ast.Name` and `ast.Constant`, none of which is deprecated; the `ast.Str` family, removed in 3.14, is not used (K4).

### Trials

- **What grimp records.** A package with every import form below, built with grimp 3.19: `import a.b.c as x`, `from <pkg> import <submodule>`, `from <pkg> import <name>`, a relative star import, imports inside a function and inside `try`, and an import under `if TYPE_CHECKING:`, each gave an edge with its line. `from <pkg> import <name that is not a module>` and an import of a module that does not exist each gave an edge to the nearest existing package. `importlib.import_module("<literal>")`, `__import__("<literal>")` and a computed name gave no edge. With `exclude_type_checking_imports=True` the `TYPE_CHECKING` import was dropped. `find_shortest_chains` found a chain through a module in no app.
- **A walk of our own against grimp.** A 50-line walk over `ast`, with the import rules of Decision 3, was run against grimp 3.19 on Django 6.1.3's own package: both found 909 modules and the same 3214 edges, with no difference in either direction. On one arm64 machine, in one run, the walk took 4.72 seconds and grimp 0.25 seconds. That is one measurement, not a benchmark (K10), and it is a cost of the walk, not a claim for it. The trial compared edges between modules of one installed package. It did not cover the mapping of first-party modules to files (Decision 3), which Django's package, with no literal dynamic imports and no namespace packages, could not exercise; those rest on the tests in Consequences.

### Forces

- **Nothing written twice.** The boundary is already stated: which apps a host holds, what each provides and requires (0021), where each app's data lives (0009), which code is which app's (Django's registry). A second statement in a linter's configuration would drift from the first.
- **Fail before deployment, with a message that names the cause** (K2, principle 6). **Running over linting** (principle 7): the check adds to the host's own checks, it does not replace them.
- **No new runtime dependency without an Accepted record** (K5). **Integrate over own** (principle 13). **Django-native** (principle 10).
- **Adoption one app at a time** (principle 9, 0003's Consequences).

## Options

1. **Wrap import-linter.** Neolith writes contracts derived from the declarations into a configuration file and runs `lint_imports`. Proven, familiar to Django teams; the configuration file and the report are import-linter's, and only imports are seen.
2. **grimp's graph, used directly, with a pass of neolith's own for everything that is not an import statement.** The commodity part comes from a maintained library; every file is read twice, by two parsers, and a native wheel is needed per CPython version.
3. **Tach.** Fast and complete for imports; its own configuration of modules and interfaces, and seven dependencies.
4. **Django system checks only**: inspect the modules loaded by the end of app loading, register the rules as checks. Django-native; sees only what was imported, and only names bound at module level.
5. **One walk of Python's own parser over each app's source, plus Django's registry and URL resolver.** No dependency; neolith owns the resolution of import statements.

## Decision

Option 5, in the nine decisions below. Each weighs its own alternatives, the other options among them (Decision 4).

### Decisions

1. **The check reports what the Accepted records forbid across a boundary, about the hosted apps' own code, and attributes each finding to one hosted app.**
   - *The rules.* Each row of the findings table comes from an Accepted record or a specification requirement named in Context, and no row comes from anywhere else: E101 to E105 from 0003 and OVR-2; E106 and E107 from 0004 and spec 05's sentence after APP-22; E108 from 0021 Decision 9 and TRN-41; E109 from 0009 open question 2, 0009's cost line on a bare `transaction.atomic()`, and 0004's "no cross-app transactions"; E110 from 0017 Decision 4 and 0022 open question 7; E111 from 0003's Context ("models, services or signals") and 0004; W102 from 0017 Decision 4 and spec 05's sentence after APP-26; W103 from 0022 Decision 7. Cross-app migration dependencies are already refused by the host (`neolith.E013`), and the check reports them as the host does (Decision 7).
   - *Whose code.* A module belongs to the app that `apps.get_containing_app_config` gives for its name (fact 1), so a nested app's modules are its own. A hosted app's code is judged. Code in no installed app, such as the project's URLconf, settings and WSGI module, is the host's composition and is not judged, except by the two warnings that 0017 and 0022 ask for there: W102 reports views in it, and W103 reports `neolith.testing.boot()` in it, where it would turn Boot's schema read off in production. An undeclared app's code is never failed: 0021 Decision 9 refuses every contract call from it, so until it has a declaration it has no other way to reach a hosted app. What it does to a hosted app is a warning against that hosted app (W105), because that is what keeps the hosted app from running detached.
   - *Contrib apps are apps* (0004). A hosted app that imports `django.contrib.auth.models` gets E102, a foreign key to `settings.AUTH_USER_MODEL` gets E106, and `get_user_model()` gets E111. A `GenericForeignKey` gets E106 through its foreign key to `ContentType`, which is how 0004's sentence on ContentType IDs shows in code. Importing a contrib app's other modules, such as `django.contrib.auth.decorators`, is importing Django, which principle 2 admits. A battery an app declares is still another app (0021 Decision 7, 0022 Decision 4): a battery with tables is admitted only in a host with a `default` and refused when the app runs alone, and E102, E106 and E111 report the use of its models before then; a battery with no models, such as `django.contrib.humanize`, gives none. An import is of a module, not of a name: `from django.contrib.auth.models import AnonymousUser` imports the module that defines `auth`'s models and loads them, so it is reported even though `AnonymousUser` is not a model.
   - *No rule on cycles.* Spring Modulith, Tach, Nx and import-linter (`independence`, `acyclic_siblings`) can each refuse cycles between modules. No Accepted record forbids a cycle of `requires`, or of imports between contract packages, and calls over HTTP tolerate one, so the check reports none. A team that wants that rule can run one of those tools beside it.
   - *Weighed: judging every installed app alike.* Simpler to state. An adopting project's undeclared apps would fail the check for the very imports they have no alternative to, and would need report-only entries, which name hosted apps only.
   - *Weighed: judging no-app code fully.* A project URLconf that imports an app's views is ordinary Django and is where 0017 binds roots by view; it is not a dependency of one app on another.
   - *The cost:* the check judges only what the host it builds holds. In a host of one app, an import of another app's internals is an import of code in no installed app, and is not reported. The guide says to run the check on a host that holds every app, as a project's own settings module does.

2. **An app's contract package, in Python terms, is the modules of the app's package that define a contract it provides, or a record or enum of one, and the package modules above them.** For each `Provided` in the app's declaration, the check takes the contract class's module and the modules of the record and enum classes reached from its actions' request, reply and error detail types, the set that the contract's description names under `$defs` (`Contract.describe`, `src/neolith/_contracts.py`). The description holds names, not classes, so the step keeps the classes that the decoration-time walk reaches, beside the description, for the check to read. Those of them inside the app's package are its contract package, together with every package module (`__init__.py`) above them up to the top-level package, since Python runs every one of them before the module itself. Such a package module may lie in the app's own package, in an outer hosted app when the app is nested in one (fact 1), or in no app. One that lies in a hosted app is held to E104 against that app's own internals; one that lies in no app is code in no app, and chains are followed from it (E103). For E103 and E104 an import of a module is also an import of each package above it; the edges of Decision 3, which the differential test compares with grimp, do not include these. A module that also defines a model, or holds the implementation of one of the app's contracts (its `Provided(implementation=...)` path), is left out and reported (E105).
   - *Imports into the contract package are free:* any app may import any module of any app's contract package, whether or not it requires that contract. OVR-1 admits the dependency, and no record ties it to `requires` (open question 4).
   - *The contract package stands alone:* a module of it, a package module above a contract module included, may import other modules of it, other apps' contract packages, and code in no app, and nothing else of its own app (E104). So importing a contract package never loads an app's internals, and spec 00's "with no implementation" holds for what a caller loads.
   - *A contract package outside every app,* such as a shared package of contracts, is code in no app: anyone may import it, and a chain through it is followed (Decision 3).
   - *Weighed: the contract class's module only.* One module per contract, simplest to state. Records would have to live in that one module, or importing it would load a module outside the contract package and fail E104.
   - *Weighed: the contract class's module and every module of the app it imports, transitively.* Nothing for an author to arrange. Any helper a contract module imports, a service module included, would become importable by every app, so the public surface would grow by accident. Packwerk's retrospective describes that drift under its privacy checks, "endless poorly-documented public code that was never meant to be public in the first place", which is part of why they left Packwerk's core in 3.0. Deriving the surface from the contract types keeps it to what a caller receives.
   - *Weighed: a naming convention*, such as `<app>.contracts`, as the README's example writes it. The host does not search by convention (0021 Decision 4), and two rules for one thing would disagree when an app keeps its records elsewhere.
   - *The cost:* a helper that a record needs, such as a validator or a constant, lives in a module of the contract package or in code in no app. An app's `__init__.py` imports nothing of the app's internals. An app that provides no contract has no contract package, and every import of its modules by another app is E101. A finding can mean that an app's layout does not match its dependencies, not only that a line is wrong; the retrospective's advice for that case is to "consider adjusting your package layout", and the guide repeats it.

3. **The check reads the source of each hosted app's package with Python's own parser, resolves import statements as Python does, maps first-party modules to files by path alone, and follows chains through first-party code in no hosted app.**
   - *Which files of an app.* Every `.py` file under the directories of the app's package, as its `__path__` lists them, at any depth, except under `__pycache__` and every file and directory whose name no dotted name reaches: one that contains a dot, other than a file's `.py`, or that is not an identifier. A symbolic link to a directory is not followed, since it can loop, so a package reached only through one is a blind spot (Decision 5). A module's name is the app's `name` and the path below it; `__init__.py` names its package. A nested hosted app's files are read as that app's. Migration modules and test modules are app code and are read (K8 asks the same of neolith's own tests).
   - *How a file is read.* Each file is parsed with `ast.parse` and its tree compiled with `compile`, and any exception from either is E112, so a file that would not import fails here too. The tree is walked without recursion (`ast.walk` or an explicit stack), so a file that compiles never ends the walk: a long chain of `+` that compiles makes a recursive `ast.NodeVisitor` raise `RecursionError`.
   - *Which statements.* Every `import` and `from ... import` in the file, wherever it stands: module level, function, class, `try`, any `if`, `if TYPE_CHECKING:` included, and Python 3.15's lazy imports (PEP 810, Final), which the tree marks with `is_lazy` and which Python admits at module level only. A type-only import is still a dependency on the other app's code, and its types are what 0003 says a caller never receives.
   - *How they resolve.* A relative name is resolved against the module's package with `importlib.util.resolve_name`; one Python would refuse gives no edge. `from <m> import <n>` is an import of `<m>.<n>` when that is a module the check knows of, and of `<m>` otherwise; `import <m>.<n> as <x>` is an import of `<m>.<n>`; a star import is an import of `<m>`. A name with no file is resolved to its nearest existing package, whatever the statement's form and however many levels are missing; a relative name past the top-level package gives no edge. For `import <m>.<missing>` these are grimp's rules, and the trial in Context found both on the same edges. grimp 3.19 differs elsewhere: `from <m>.<missing> import <n>`, and a name missing two levels down, give it no edge, and a relative `from` past the top level makes it raise `PanicException`; the differential test leaves those forms out and tests them on their own.
   - *How a name is resolved.* Each import statement in the module's own scope, wherever it stands there (in `if`, `try`, `with`, `for`, `while` and `match` blocks, at any depth), is a top-level import and binds names to dotted names: `import a.b` binds `a` to `a`; `import a.b as x` binds `x` to `a.b`; `from a import b [as x]` binds `b` (or `x`) to `a.b`, with a relative `a` resolved as above. An attribute chain on a bound name extends its dotted name, so `testing.boot` after `from neolith import testing`, and `neolith.testing.boot` after `import neolith.testing`, both resolve to `neolith.testing.boot`. The check follows only these top-level imports, and only for a name the file binds in no other way. A name is followed when every top-level import of it gives one dotted name, or dotted names that stand for one listed object, as the compatibility form `try: from django.urls import include` / `except ImportError: from django.conf.urls import include` does, and when nothing else in the file can bind it. Whether anything else can is read from the standard library's `symtable`, which `compile` builds for every file anyway, and from the tree: the name is not followed anywhere in the file when a table of any scope marks it `is_assigned()`, `is_parameter()`, `is_declared_global()` or `is_nonlocal()`, or `is_imported()` in a scope other than the module's, or when it is the target of a comprehension, which Python 3.12 folds into the scope around it with no table of its own (PEP 709). No name is followed in a file that has a `from <m> import *`: Python binds every public name of `<m>` there, and neither `symtable` nor the tree shows which. `is_declared_global()` also covers an assignment expression in a comprehension at module level, which `symtable` marks only that way. The rule is conservative on purpose: a name it does not follow is a blind spot that Decision 5 lists, never a finding, so a form it misjudges can hide a finding but not raise a false one, unless that form binds the name in a way neither `symtable` nor the tree shows. Two such ways remain: a star import, which the rule handles above, and a write through `exec`, `globals()` or the module object, which Decision 5 lists; a probe of the product below on Python 3.13 (83 fixtures) found no other. Python's binding forms are a closed list (the language reference, *Binding of names*): assignment and augmented assignment, annotated assignment, `import` and `from ... import`, `def`, `class`, `type`, `for`, `with ... as`, `except ... as`, `:=`, `del`, `match` captures, type parameters and comprehension targets. A test generates every form, placed directly in each kind of scope (module, function, class, type-parameter scope) and inside an inlined comprehension in each, under no declaration, `global` and `nonlocal`, drops the combinations that are a `SyntaxError`, runs each under the interpreter, and checks that a name the rule follows reaches the imported object; a difference is a rule to fix. The rows of the findings table that name a function, a constant or an object of a module match the resolved name, never the spelling: `neolith.connect` (E108), `neolith.command_scope` (E110), `neolith.testing.boot` (W103), `django.contrib.auth.get_user_model` (E111), `importlib.import_module`, `django.utils.module_loading.import_string`, and `django.urls.include` (literal dynamic imports), and for E109 the functions of `django.db.transaction`, `django.db.connection`, `django.db.connections`, and `DEFAULT_DB_ALIAS` from `django.db` or `django.db.utils`, which is read as the literal `"default"`. `__import__` is matched as the builtin only when the file binds it nowhere: no table of any scope marks it `is_imported()`, `is_assigned()`, `is_parameter()`, `is_declared_global()` or `is_nonlocal()`, it is no comprehension target, and the file has no `from <m> import *`. `get_model`, `get_app_config` and `sender=` are matched by attribute or keyword name, whatever the receiver (Decision 5). Each listed name stands for its object: the check matches the module that defines it and every module of the installed Django and of neolith whose `__all__` lists the same name, bound to the same object. The walk that finds them imports every module of Django and of neolith, so it runs in a test that pins the set on both Django versions, not in the check; the check carries the set as data. On 6.1.3 the walk gives `django.urls.conf` (which defines `include`), `django.urls` and `django.conf.urls` for `include`, and `django.db.utils` (which defines `DEFAULT_DB_ALIAS`) and `django.db` for `DEFAULT_DB_ALIAS`; the other names have no re-export.
   - *Literal dynamic imports.* `importlib.import_module("<name>")`, with a literal package given as `package=` or as the second positional argument, or `__package__` in either place, for a relative name; `__import__("<name>")`; `import_string("<path>")` (its module); and `include("<module>")` or `include(("<module>", "<app_name>"))`, a 2-tuple, the one tuple Django imports from, are imports of that module, at that line (facts 2 and 3). A computed package is W101. `include` with any other argument gives nothing: Django imports only a `str` there (`urls/conf.py`), and the common computed arguments, such as `router.urls` or `admin.site.urls`, are lists of patterns, not names.
   - *First-party directories.* A *first-party directory* is a directory from which a hosted app's top-level package, or the settings module's top-level package, is imported, unless it is one of the interpreter's library directories or lies under one. The library directories are those `sysconfig.get_paths()` gives for `stdlib`, `platstdlib`, `purelib` and `platlib`, and every directory that `site.getsitepackages()` and `site.getusersitepackages()` report; on a Debian system Python the second set holds `/usr/lib/python3/dist-packages`, which the first does not, and the user site holds what `pip install --user` installs. The settings module's directory is included so that a project whose apps are installed as distributions still has its URLconf, settings and WSGI module read for W102 and W103.
   - *How a dotted name is placed, without running code.* The check walks each first-party directory by path and builds a map from dotted names to files: a file's name is its path below the first-party directory, `__init__.py` names its package, and a directory with no `__init__.py` is a portion of a namespace package, as Python's path finder treats it. The walk skips `__pycache__`, the names no dotted name reaches as above, symbolic links to directories, and directories that hold a `pyvenv.cfg`, which are virtual environments. Where one first-party directory lies inside another, each file is named from the innermost. Where one dotted name has two files, the map takes the one Python's path finder imports: a regular package before a module of the same name in one directory, a package or module before a namespace portion, and the first-party directories in `sys.path` order. A dotted name is first-party when the map holds it, and nothing else is. The check never imports a module and never calls `importlib.util.find_spec` on a dotted name to place it, since that runs the name's parent packages. A package that changes its `__path__` at run time, and a `.pth` file, are not followed (Decision 5).
   - *Chains.* When an app's module imports a first-party module in no hosted app, the check reads it, and the modules it imports in turn, through first-party modules in no hosted app only. A chain that reaches what E101 or E102 would report is E103, at the app's import line, with one shortest chain named. The check never follows a chain into a hosted app's module or an app's contract package: each app's own imports are judged for that app, so a chain through them would report one mistake twice. A first-party module in no app that cannot be read or compiled ends its chain, with no finding.
   - *W103 reads every first-party file* of the map other than a test module, in apps and in no app. A test module is named by its file: `conftest.py`, `tests.py`, `test_*.py`, `*_test.py`, or any file under a directory named `tests`. These are the names pytest and `startapp` use; a test helper named otherwise gets W103, which is a warning.
   - *Undeclared apps' code* is read when its package lies under a first-party directory, for W105 only. Contrib and third-party apps live in library directories and are not read.
   - *Weighed: direct imports only*, as Tach checks. Smaller. `<a>` importing a project helper that imports `<b>.models` depends on `<b>`'s internals as surely as a direct import, which OVR-2's "depend" covers; it is the shared-helper coupling that most often blocks a split.
   - *Weighed: following every module of every package the apps import.* No first-party rule needed. It would read Django and every library on each run.
   - *Weighed: excluding `TYPE_CHECKING` imports*, as grimp offers. A second rule for one statement, and annotations that name another app's models are still a dependency on them.
   - *Weighed: leaving chains (E103) and undeclared apps (W105) to a later record.* No Accepted record names chains through code in no app, and this part has the least trial behind it. It would leave out the shared-helper case above, and the map from names to files is needed anyway for W102 and W103 in code in no app. It is kept, with its lookup stated here and its tests named in Consequences.
   - *The cost:* a first-party package installed into the interpreter's library directories, or found through a path the hosted apps and the settings module are not imported from, is not followed (open question 2). A package that builds its `__path__` at run time is placed only where its files lie.

4. **The engine is Python's `ast`, `symtable`, `importlib.util`, `inspect`, `site`, `sysconfig` and `tomllib`, and Django's registry and URL resolver. The check adds no dependency, neither a runtime one nor an optional extra, and narrows one sentence of 0003.**
   - *Why:* half of what the Accepted records ask the check to find is not an import statement: `connect()` literals against `requires`, alias literals and the forms that mean `default`, command scope labels, model strings, `testing.boot()`, relations between models, views in no app. Every option therefore needs a walk of neolith's own over each file. Once that walk exists, resolving import statements in it is a small part of it (the trial's walk is about 50 lines and agreed with grimp edge for edge on Django's 909 modules), and one parse gives imports and literals the same module names and line numbers. The parser is the running interpreter's own, so it reads new syntax, such as lazy imports, on the day that Python does, and a file that would not import fails the same way (E112). It also sees literal dynamic imports, which grimp does not (trial).
   - *K5 is met without a library.* `ast`, `symtable`, `importlib.util`, `inspect`, `site`, `sysconfig` and `tomllib` are in the standard library of every supported Python, and the registry and resolver are Django's.
   - *Weighed: wrapping import-linter 2.16* (option 1). It is maintained, BSD 2-Clause and typed, and a team may well run it beside neolith for its own layering or cycle rules. As neolith's engine, its public API takes contracts from a file (`lint_imports(config_filename)`), so neolith would write a generated configuration on each run, or call `create_report` from its `importlinter.application` package, outside the documented API. The report would be import-linter's, rendered with `rich`, not the one-line findings of Decision 8; a per-app mode would mean one run per mode; and three packages (click, rich, grimp, with rich's own two, markdown-it-py and Pygments, and markdown-it-py's mdurl) would come with it. Its `protected` contract is close to E101 for direct imports, and nothing in it sees the other rows.
   - *Weighed: grimp 3.19 used directly* (option 2). This was the closest alternative. It is BSD 2-Clause, has no dependencies of its own, is typed, has documented graph queries with line numbers and chains, is fast (0.25 seconds against the walk's 4.72 on the trial), and has shipped wheels for each new CPython promptly. As an optional extra used only by the command it would not be a dependency of every adopter. Against it: the walk of neolith's own still reads every file for the rows that are not imports, so every file is parsed twice, by two parsers that must agree on module names; literal dynamic imports would come from the second parser anyway; grimp is a native extension per CPython minor version and CPython only, so a new interpreter or a platform without a wheel needs a Rust toolchain; its default writes a cache into the working directory. For a command that runs once per CI job, the time saved did not outweigh a second parser.
   - *Weighed: Tach 0.35.3* (option 3). MIT and fast. Its `tach.toml` restates modules, dependencies and interfaces that the declarations already state, which is the duplication the first force rules out, and it brings seven dependencies.
   - *Weighed: Django system checks as the engine* (option 4). The checks that need the registry, models and the URL resolver, use it here. For imports, a check that inspects the modules loaded by the end of app loading sees only what was imported by then and only names bound at module level; a function-level import is invisible, and importing every module to see it runs side effects Django leaves lazy (0021 Decision 10 weighed the same). As the form of the findings, see Decisions 8 and 9.
   - *Principle 13.* Integrating is the default. The part of this work that exists elsewhere, resolving import statements, is small and is done here with the standard library; the parts no tool offers are derived from neolith's own declarations. [0028](0028-the-http-transport-uses-the-standard-library-only.md) weighed the same principle for the HTTP client and also added no runtime dependency.
   - **The narrowing (D2).** 0003's Decision says: "A **neolith check**, built on existing import linting, enforces the boundary in CI." Whether "existing import linting" names a technique or a tool is open to reading; the roadmap reads it as a tool. To leave no doubt, this record narrows that sentence to: a neolith check, built on Python's own parser and Django's app registry, enforces the boundary in CI, and adds no import linter as a dependency. The pull request that accepts this record adds the line `Narrowed by 0030 (Decision 4)` under 0003's status, as a link, and nothing else in 0003 changes; the roadmap's step 7 row and its note on import-linter change in that pull request too.
   - *The cost:* neolith owns the resolution of import statements and the map from names to files, and their correctness rests on its own tests (Consequences). The walk is slower than grimp's scanner by about twenty times on the one trial. Packwerk and grimp each met that cost on large codebases with a per-file cache; a cache keyed by each file's content, kept outside the working tree, can come later in a pull request that brings its measurement (K10).

5. **What the check can and cannot see, stated plainly.**

   **It sees:**
   - every `import` and `from ... import` statement in an app's files, wherever it stands, `TYPE_CHECKING` and lazy imports included;
   - `import_module`, `__import__`, `import_string` and `include` with a literal name (`include` also with a 2-tuple whose first item is one), and `import_module`'s package as a keyword or the second positional argument (Decision 3);
   - a call or a name whose resolved name (Decision 3) is `neolith.connect`, `neolith.command_scope`, `neolith.testing.boot`, `django.contrib.auth.get_user_model`, a function of `django.db.transaction`, `django.db.connection`, `django.db.connections` or `DEFAULT_DB_ALIAS`, however the file imported it at its top level: from the module, from its package, under an alias, or through an attribute chain, for a name the file binds in no other way (Decision 3);
   - any call of an attribute named `get_model` with literal arguments that include a label, and any call of an attribute named `get_app_config` with a literal label, whatever the receiver, since migrations receive the registry as a parameter; any keyword `sender=` whose literal has the form `<label>.<Model>` with `<label>` an installed app's label;
   - an alias written as a literal, or as `DEFAULT_DB_ALIAS`, in these places only: any keyword `using=`, the positional place of `using` in a call of a function of `django.db.transaction` (its place in that function's signature), the first argument of a method call `.using(...)` or `.db_manager(...)`, and the subscript of `django.db.connections`. Only an alias that is another hosted app's label, or `default`, is reported; a literal that names no alias of the host is Django's error at run time;
   - the forms that mean `default` by leaving the alias out: each public function of `django.db.transaction` whose signature, read with `inspect.signature` from the installed Django, has a parameter named `using`, called with no alias or with `None` (on 5.2.19 fifteen functions; 6.1.3 adds `savepoint_create`, which `savepoint` now calls after a deprecation warning); `atomic` and `non_atomic_requests` used as a bare decorator, which both read as `default` (their `callable(using)` branch, `db/transaction.py`); and `django.db.connection`, at its import or attribute access. A test compares the set with the installed module on both Django versions. In a host built by 0009, `default` is never a hosted app's own alias, so each of these misses the app's own database;
   - every relation, proxy and table name of every model in the registry, with lazy string references already resolved by Django (fact 2);
   - every view reachable from `ROOT_URLCONF`, judged by the same function that binds request roots, so the check and the host agree on which app serves it.

   **It cannot see, and says so:**
   - *a computed argument* to the calls above, such as `connect(name)`, `get_model(label, model)` or `import_module(".x", name)`. The call site is reported as `neolith.W101`, so the blind spot is listed, not silent. `include` is the exception: its computed arguments are most often lists of patterns (Decision 3), so a computed module name there is neither seen nor reported. A computed alias (`using=self._db`) is not reported: it is common in managers and routers, and a warning there would bury the others;
   - *a model named without its app*: `get_model("<Model>")` with one argument, on a config the check cannot place. When the config came from `get_app_config("<label>")` of another app, that call is E111; otherwise nothing is reported;
   - *a name bound other than by top-level imports alone* (Decision 3): an import inside a function or a class, a parameter, an assignment, a loop target, an annotation, with or without a value, a `global` or `nonlocal` declaration, or a comprehension target of the same name anywhere in the file, any of which stops that name being followed in the whole file, and every name in a file that has a `from <m> import *`, or that the file rebinds through `exec`, `globals()` or the module object. A call through such a name is not judged, except a name rebound through `exec`, `globals()` or the module object, which the check cannot see and judges as its import; under E108 and E110 the host's own refusals at run time remain (0021 Decision 9). Also not followed: a project's own constant for an alias (`ALIAS = "other"` followed by `using=ALIAS`), which is a computed alias; and *a call through another reference*, such as `c = connect` followed by `c("<id>")`, `functools.partial(connect, ...)`, a callee from another module, or an attribute of an object passed in; also a library helper that leaves `using` out inside its own code;
   - *any other way to load code*: `importlib.util.spec_from_file_location`, `runpy`, `pkgutil`, `exec`, `eval`, a lookup in `sys.modules`, a package `__getattr__` or a `__path__` changed at run time, a `.pth` file, a string handed to a library that imports it later (a task name, a setting);
   - *data reached without a model*: raw SQL naming another app's table (`cursor.execute`, `raw`, `extra`), a table name that matches no model in the host, and lookups through `ContentType`, such as `ContentType.objects.get_by_natural_key("<label>", "<model>").model_class()` or `get_for_id`, which name a model by data;
   - *objects handed over at run time*: an ORM object from code in no app, `request.user`, a signal receiver connected with a model object that code in no app passed in;
   - *code that runs in another app's root*: E108 and E110 judge a call by the app whose module holds it, while 0021 Decision 9 judges the app of the scope the call runs in. Middleware, a template tag or a signal receiver of `<a>` that runs in `<b>`'s root can pass the check and be refused when it runs;
   - *a `connect()` literal in code in no app*, such as a helper that an app's module calls. Code in no app is not judged (Decision 1), while 0029 ties such a call, when it runs during loading, to the app whose loading step asked for it, which only running shows. An identity the host does not know is still refused at set-up or at the `connect()` line (0021 Decision 10), and a call outside the calling app's `requires` when it runs (0021 Decision 9);
   - *views not reached from `ROOT_URLCONF`*: a URLconf a middleware sets per request through `request.urlconf` (as django-hosts does), and routing built in `asgi.py`, such as Channels consumers or a mounted ASGI app. Sentence (d) of the specification delta is worded for what the URL configuration reaches;
   - *templates*: `{% load %}` of another app's tag library, `{% include %}` of another app's template, and `reverse()` of another app's URL name;
   - *files without Python source* (W104), files of a package reached only through a symbolic link to a directory (Decision 3), and every file of an app outside the host the check builds (Decision 1's cost).

   These limits are those of reading code without running it. A rule that relied on them would erode silently, which is 0003's reason for the check; the host's runtime checks stay the backstop: 0021 Decision 9 on each call, 0009's router on each relation, and 0017 Decision 4's root with no app for a request no app serves. Principle 7 asks that every app boot alone and pass its tests.
   - *Weighed: a warning for every string that looks like a dotted path or a label.* It would cover more, and report every log message and template name that happens to match.
   - *Weighed: refusing computed arguments outright.* The check would then forbid code that the host runs correctly, such as a provider that connects to a contract version chosen by configuration.

6. **Each hosted app is enforced, unless the repository lists it in `[tool.neolith] boundary-report-only` in its `pyproject.toml`. That key is the only place the mode is set, and only the check reads it.**
   - *Enforced:* an error finding of the app makes the check exit 1. *Report-only:* its error findings are printed, marked `(report only)`, counted in the summary, and do not change the exit status. Warnings never change it, and host refusals always do, in both modes.
   - *Enforce is the default*, so an app is enforced from its first commit unless someone writes its label in the key: a new project needs no entry, and an adopting project lists the apps it is still untangling (0003's Consequences, principle 9).
   - *A stale entry is an error* (E113): a listed app with no error finding is reported, with status 1, until its label is removed. An entry that hides nothing would hide the app's next finding. import-linter treats an `ignore_imports` entry that matches nothing as an error by default for the same reason (`unmatched_ignore_imports_alerting`, `importlinter/contracts/protected.py`), and ESLint's suppressions report unused entries.
   - *Labels, not package paths,* because hosted apps are named by label everywhere inside `NEOLITH` (`DATABASES` keys, 0009) and in `principal_from` (0021). A label that is not a hosted app of the host the check builds is refused, since the check is meant to run on a host that holds every app (Decision 1's cost).
   - *Why `pyproject.toml`.* The mode is the posture of one repository's CI, not a property of the app in every host, nor of one deployment. A repository has one `pyproject.toml`, it does not vary by environment, and it never ships as a production settings module. No host reads it, so a lint setting can never stop a host that serves. That is where the compared tools keep enforcement posture: import-linter in `.importlinter` or `pyproject.toml`, Tach in `tach.toml` with a per-module `unchecked` flag, deptrac in `deptrac.yaml`, Packwerk in each package's `package.yml`. The file is read with `tomllib`, and the table admits this one key, closed as 0021 closes a declaration's namespace.
   - *Two modes, no third.* There is no mode that hides an app's findings, and no per-line or per-import exemption.
   - *Weighed: a key in `NEOLITH`, checked by the builder at Configure* (an earlier draft of this record). Every run against a host would read it, and the builder would check its labels. But 0009 makes deployer modules per host, and projects often keep several settings modules, such as base, development, CI and production; each can list different apps, which is writing the mode once per module, the cost held against a command-line flag below. A key checked at Configure would also let a lint setting stop a host from serving: a base module shared by single-app production hosts that lists another app's label would be refused at start-up. And the key would ship in production settings that nothing at run time reads. Having only the check read the key would remove the second cost and keep the other two.
   - *Weighed: a field on the declaration*, as Spring Modulith marks an open module in its own code and Packwerk sets `enforce_dependencies` beside each package, the closest precedent. The mode would travel with the app. Spec 05 fixes a declaration's fields, 0021 closes its namespace, and the mode is one repository's posture, not something every host of the app should read.
   - *Weighed: a command-line flag*, such as the roadmap sketch's `neolith check [--report]`, or one flag per app. CI policy would sit in CI configuration. A developer's local run would then disagree with CI unless the flags were copied, which is writing the mode twice.
   - *Weighed: exemptions per import*, as import-linter's `ignore_imports` and per-line comments in linters. They let a nearly clean app be enforced. They are a second statement of the boundary, line by line, written by hand, and the first form of adoption 0003 names is per app.
   - *Weighed: a generated baseline of current findings*, as Packwerk's `package_todo.yml` written by `update-todo`, ArchUnit's `FreezingArchRule`, deptrac's baseline formatter and ESLint's bulk suppressions. A command writes it, never a hand; the check then fails only on findings not in it, and drops entries for findings that are gone. Because it is generated, it does not restate the boundary, and it closes the cost below: an app under adoption could not gain a new finding without CI failing. It is not in this record for three reasons. A baseline needs an identity for a finding that survives edits around it (ArchUnit ignores line numbers; Packwerk keys by file and constant), and this record defines none. It needs a rule on who may regenerate it, since a regenerated baseline admits a new finding as easily as a report-only entry does; Packwerk's retrospective reports that "With every new feature added, these todo files grew larger", and ArchUnit refuses to create a store unless told to but updates one by default. And 0003's Consequences name per-app adoption, which the key gives today. A baseline can be added later without changing an id or a line of output; open question 1 names it as the candidate.
   - *The cost, accepted:* one remaining finding keeps a whole app report-only, and while it is, a new finding in that app is printed and counted but does not fail CI. A regression in an app under adoption is visible, not stopped. The summary line counts errors in report-only apps apart, so a CI job or a reviewer can watch that number fall; a ratchet is left to open question 1.

7. **One command, `checkapps`, with two entries. It runs no Django system check of its own, then the host's startup checks that read no database, then the boundary pass, and its own work opens no database connection.** This follows 0022 Decision 11's shape for `migrateapps`.
   - *Entries.* `manage.py checkapps` checks a settings-module host, such as an existing project with a real `default` and undeclared apps. `neolith check <app> [<app> ...] --settings <module>` builds a closed host from the deployer's module, as `neolith run` does, and runs the same command. Once the command runs, both entries run the same code, print the same findings and summary for the same host, and exit with the same statuses, since the command writes its own lines and exits itself rather than raising to Django. Before it runs they differ, because `manage.py` loads apps before it looks up the command (fact 7): there, a refusal from the builder or from set-up keeps Django's form, a traceback, and ends the process with Python's status 1, where `neolith check` prints it as `neolith: <message>`, status 1.
   - *No Django checks before the command.* `checkapps` sets `requires_system_checks = []`, as Django's own `check` command does. With Django's default, which `migrateapps` keeps, `BaseCommand.execute` runs every registered check with no `databases`, and on 6.1 that asks each alias's features and can open a connection before the command starts (fact 4). The checks under the tag `neolith` already run in set-up (phase 3), so nothing is printed twice. Django's own checks stay with Django's `check` command.
   - *Phases, in order.* (1) Arguments, and the shape of `[tool.neolith]`: its keys, the list's type, empty and repeated entries, status 2 on a mistake. (2) The builder's Declare, Resolve and Configure (0022 Decision 1). (3) Django loads apps, which runs set-up: Resolve and Validate, which imports and builds each implementation (0021 Decision 5), `neolith.E005` at a process's first set-up, and every check registered under the tag `neolith` other than those registered with `deploy=True` (0022 Decision 5): today `neolith.E001` to `E004`, `E006`, `E014` to `E017`, `E019` to `E021`, `W001`, `W004` and `W005` (`register`, `src/neolith/_checks.py`), and not `W006`, which runs under `check --deploy` only. Once phase 3 has given the hosted apps, a `boundary-report-only` label that is not one of them is refused, status 2; it cannot be decided earlier, since the labels come from Declare. A refusal in phases 2 and 3 ends the run with status 1, in the form the entry gives it, since the registry the later phases read is not there. (4) Boot's checks that read no database: `ROOT_URLCONF` is set and imports; `neolith.W001` again for admins registered by the URLconf; the code checks of the schema step, `neolith.E008`, `E010` for migrations that cannot be loaded, `E011` and `E013` (`code_messages`, `src/neolith/_boot.py`); and any later Boot check that reads no database, such as the `neolith.W003` that 0011 gives Boot for a deployer URL the host shadows. (5) The boundary pass. Phases 4 and 5 both run and are reported together; W102 is skipped when `ROOT_URLCONF` did not import.
   - *What is not run:* Boot's reads of a database, `neolith.E007`, `E009`, `E010` for a recorded history, `E012` and `E018`. `migrateapps --check` runs them against the real databases (0022 Decision 7), so CI can run the check with no database and the release pipeline runs the schema check where the databases are. The check calls Boot's functions directly and never `boot()`, so it keeps no Boot outcome and marks nothing booted.
   - *The guard.* For the length of the command, `BaseDatabaseWrapper.connect` is replaced with a function that raises `neolith.UsageError` (0021 Decision 9) with `check: database <alias>: a connection was opened while the host was set up or checked, and the check runs without a database`, and restored when the command ends. The message names what happened, not who did it: a connection can come from app code, from a URLconf import, or from a library. `connect` is the one path to a new connection in every backend Django ships (fact 5), which is why it is the point chosen; Django's own test framework guards the same way, at `ensure_connection`. Django's `DatabaseOperationForbidden` is not used: it is an undocumented `AssertionError` subclass in `django.test.testcases`, and using it would import Django's test machinery into a command.
   - *What the guard covers.* Under `neolith check` the guard is in place before Django loads apps, so app code that queries while loading fails with that message as the cause of the builder's or set-up's refusal. Under `manage.py checkapps`, Django has loaded apps before the command starts, so the guard covers phases 4 and 5 only, and app code that queries while apps load is not guarded there; with `requires_system_checks = []`, nothing of Django's own opens a connection before the command.
   - *The command owns its process.* The replacement is on the class, for the whole process, so a `call_command("checkapps")` in a process with other threads, such as a test with a live server, refuses their new connections while it runs. The command is documented as one for a process of its own, and the replacement as state it owns (K6). It is the same on both Django versions.
   - *Not the pass-through.* `neolith check` is a second named entry of the kind 0022 open question 4 weighs, as `neolith migrate` is the first; this record does not settle that question, and either name can become an alias of a pass-through later.
   - *Weighed: one entry only, `neolith check`.* An existing project with undeclared apps on a real `default` could not be checked, since `neolith check` builds closed hosts, as `neolith run` does in 0.1.
   - *Weighed: running Boot in full with `neolith.testing.boot()`'s switch.* It would mark the process booted and keep an outcome the check has no use for.
   - *Weighed: Django's `databases` convention alone.* Django keeps database checks out by giving them no alias (`check --database`, `SimpleTestCase.databases`), and `requires_system_checks = []` applies that convention here: nothing the command calls is given an alias. It does not cover app code that queries while apps load, or a URLconf that queries at import, so the guard stays as the backstop.
   - *Weighed: running Django's own static checks too*, with `checks.run_checks(databases=[])`, which asks no alias on either version. One CI command would cover both. Django's messages would then print in Django's form beside the one-line findings, and the checks that need an alias would be skipped without a word; `manage.py check`, where `--database` chooses the aliases, stays the place for them.
   - *Weighed: no guard.* Simpler. A query while apps load would then create an empty SQLite file in the working tree, which Boot later refuses (`neolith.E018`), or fail on a missing server with that driver's message.

8. **Findings are one line each on standard output; host refusals keep the host's form on standard error; the exit status is 0, 1 or 2.**
   - *A finding:* `<path>:<line>: <id> <message>`, with ` (report only)` after an error of a report-only app. A finding with no place in source (E113) is `<id> <message>`. `<path>` is relative to the working directory when the file lies under it, and absolute otherwise, with each control, format or line-ending character, and each lone surrogate, written as its Python escape, so a finding stays one line. A model's place is its class's first line; a view's is its function's. Findings are sorted by path, line and id, and each is printed once; a finding with no place in source comes after them, sorted by id and then label. Every message names its app first, as 0022's messages do, then the module or model, then what to do; the table above gives the cases.
   - *Built as Django's check messages.* Each finding is a `django.core.checks.Error` or `Warning` with `msg`, `hint` (what to do), `obj` and `id`, never registered (Decision 9), and the line prints `<msg>; <hint>`. An API that hands findings to Django code later then needs no second form.
   - *The summary:* the last line is `neolith check: <n> errors, <m> errors in report-only apps, <k> warnings`, also when all three are 0.
   - *Host refusals and warnings* met while the command runs are printed as the `neolith` script prints them, `neolith: <message>` (0022 Decision 12) and `neolith: warning: <message>` (`_HostLog`, `src/neolith/_cli.py`), on standard error; `neolith` attaches that handler in `main` only, so the command attaches it itself for the length of its run under both entries, so that one host gives one message for one problem, whichever command meets it. They reach CI logs as they are: 0022's `neolith.E005` names the first value of `DATABASES` that differs from what the host builds, which can be a password. This record does not change that message; leaving connection values out of E005 is a change of its own.
   - *Exit statuses.* `0`: no host refusal, no error finding of an enforced app, no E113. `1`: any of those. `2`: an argument mistake, a refusal of `[tool.neolith]`, or an error the check did not foresee, printed as `neolith: check: internal error: ...`. This extends 0022 Decision 12, where a refusal is status 1 and an argument mistake status 2, with the convention of linters that keep `2` for a run that could not finish, so a crash of the check is never read as findings. `migrateapps --check` itself exits with 0 or 1.
   - *Weighed: a machine format*, such as JSON or SARIF for code scanning. A second form of every message; open question 3.
   - *Weighed: a status that tells host refusals from findings.* CI acts on both the same way, and the printed lines already tell them apart.
   - *Weighed: `--fail-level`*, as Django's `check` offers, so that a team could fail on warnings. A flag that changes the outcome is CI policy outside the repository, the cost Decision 6 weighed for a flag; and W101 and W105 report places the check cannot judge or another team's code, so failing on them would push authors to drop computed arguments, which Decision 5 weighed.
   - *Weighed: app labels to narrow the output*, as `check` takes them. A run over part of a host can pass where the whole fails, and the per-app mode already says which apps fail the run.

9. **The boundary pass is not a Django system check and is not run at start-up.**
   - *Not registered with Django's registry.* Every management command runs every registered check by default (fact 4), so `migrate`, `runserver` and `shell` would each read every source file of every app. Registering with `deploy=True` would keep it out of them, but `check --deploy` is Django's audit of production settings. A report-only app would also need a level that depends on configuration, where Django's id letter states the level, and `SILENCED_SYSTEM_CHECKS` would become a second way to hide a warning. What is kept from the framework is its message type and its id form, `neolith.E1NN` and `neolith.W1NN`, whose letter gives the level whatever the mode.
   - *Not at start-up.* The findings are about source, which does not change between CI and deployment, and reading it costs seconds (the trial read Django's source in 4.72 seconds). The host's own checks stay where 0022 puts them. Principle 7 holds: the check adds to running alone, it does not stand in for it.
   - *Weighed: running the pass in set-up, as K2 would suggest for anything that can fail.* A boundary finding does not fail at first use; it fails at detach, and the check runs before that in CI.
   - **The narrowing of 0017 (D2).** 0017 Decision 4 says: "A view whose code is in no installed app, including a project-level admin class, gives a root with no app, so calls from it have no caller and are refused (0010 Decision 7), and `neolith check` warns about such views at startup (K2)." This record narrows its last clause to: `neolith check` warns, before deployment, about each such view whose code lies under a first-party directory (W102), and the host warns at startup about admin classes in no installed app, as `neolith.W001` does today. Two things change. *When:* the warning comes from the check in CI, not from each start of a host, for the reasons above. *Which views:* Django's generic views, `static.serve` and a library's views in a project URLconf run no first-party code, so a warning about each, at every run, would bury the views a project wrote. 0022's admitted set, in its row for a `ModelAdmin` class in no installed app, says: "0017 asks `neolith check` to warn about every view in no installed app; step 4 ships the admin-class part, as #11 plans, and the rest arrives with `neolith check` (step 7, #14)." This record narrows "every view in no installed app" there in the same way. The pull request that accepts this record adds `Narrowed by 0030 (Decision 9)` under the status of 0017 and of 0022, and nothing else in either changes.
   - *Weighed: W102 at Boot, for every view in no installed app, as 0017's sentence reads.* Boot already imports the URLconf and warns about admin classes again (`neolith.W001`), so a walk of the resolver with `label_of` would cost little. It would warn at every start of every host for each generic view and `static.serve` in a project URLconf, and the filter that keeps those out needs the map of first-party files (Decision 3), which Boot does not build. The cost of the narrowing: a host started without the check in its CI gives no warning for a first-party view in no app, and a call from that view is refused when it runs (0010 Decision 7), which is 0017's own backstop.

### Specification delta

The specification gains, in the step 7 pull request that ships the check, with IDs assigned there (P5) and in its own words (P2), a section of spec 05, *The check before deployment*. Its lead-in, which carries no ID, says that an implementation should offer a check, run before deployment, that reports, one requirement each:

- (a) each dependency of an app's code on anything of another app other than that app's contract package (spec 00, OVR-2);
- (b) each relation in an app's data model to records of another app, and each record type of an app stored where another app's records are;
- (c) each place in an app's code that uses a database other than the app's own, whether it names that database or leaves the database unnamed, or that opens a root naming another app;
- (d) each piece of the project's own code in no app that serves requests reachable from the host's URL configuration.

And two requirements of their own: (e) a check offered under (a) to (d) must not itself open a connection to a database; (f) such a check may let a project choose, per app, whether that app's reports end the check with an outcome that differs from a check that reports none.

They are APP-66 to APP-71, (a) to (f) in that order. TRN-41 already covers calls to a contract version outside `requires`. The `[not-tested]` entry for OVR-2 in `tests/spec_trace.toml` keeps its place, since OVR-2 binds app code, with its reason changed to say that the check before deployment reports it, citing (a)'s ID. The text after APP-22 and after APP-26 then refers to the new section, and the sentence after APP-26, "Other code in no app that serves requests is found by the check before deployment", is reworded to match (d).

Follows principles 2 (*contracts over imports*), 4 (*owned data over shared data*), 6 (*visible failure over transparent calls*), 7 (*running over linting*), 9 (*new and existing projects alike*), 10 (*Django-native over framework-new*) and 13 (*integrate over own*, weighed under Decision 4). No decision here adds a runtime dependency (K5).

## Consequences

- The boundary is stated once, in the declarations, and checked from them. A project writes nothing for the check except, while it adopts, the labels in `[tool.neolith] boundary-report-only`. No host reads that key, so it cannot stop a host from serving.
- `connect()` literals outside `requires` (TRN-41), alias literals and the bare forms that mean `default` (0009), scopes for other apps (0022) and views in no app (0017) are found before deployment, closing the gaps those records left to step 7. Unknown identities in modules imported late, 0021 Decision 10's known gap, are found as E108, since an identity no declaration names is in no app's `requires`.
- An app that keeps records beside its models, or its implementation beside its contract, or whose `__init__.py` imports its internals, gets E104 or E105 and has to move them. The README's example, a contract in `<app>/contracts.py` with its records, is already in the admitted form.
- A hosted app that imports `django.contrib.auth.models` or calls `get_user_model()` is reported, as 0004 already says of foreign keys to `auth.User`. How contrib apps are hosted per app stays the repository's [open question 4](../open-questions.md); until it is settled, an app that needs `auth` stays report-only or uses the principal (0023).
- A hosted app that writes a bare `transaction.atomic()` or uses `django.db.connection` is reported, and names its own alias instead, which 0009 already asks.
- An app whose existing migrations import another app's helper stays report-only until those migrations are squashed or the helper is copied into them, since there is no per-import exemption.
- W102 reports only views whose code lies under a first-party directory, so Django's generic views, `static.serve` and a library's views in a project URLconf are not reported: they run no first-party code in no app. A first-party view in no app is. This and the check's place in CI narrow 0017 Decision 4's last clause (Decision 9).
- Undeclared apps are never failed. Their reach into a hosted app is a warning against that app, so the team that owns it sees what stands between it and running alone.
- The check runs in CI with no database. The schema check stays `migrateapps --check`, which needs one. Django's own `check` stays a separate command; on 6.1 it asks each alias's features as Django documents.
- The check builds and sets up the host, so CI needs a settings module that the builder and set-up admit. Where that module reads values from the environment, such as 0027's `SIGNING_SECRETS`, CI gives it values the builder admits; the check makes no contract call of its own, so they need not be the production ones.
- Host refusals reach CI logs as the host prints them, so a settings module that sets a database password after the builder call can show it in `neolith.E005`. Leaving connection values out of that message is a change of its own.
- The public surface gains `neolith check`, the `checkapps` command, the `[tool.neolith] boundary-report-only` key, and the ids `neolith.E101` to `E113` and `neolith.W101` to `W105`, each fixed by the pull request that ships it. 0022's key table does not change.
- The pull request that accepts this record, the first to carry code built on it, also changes: 0003, which gains `Narrowed by 0030 (Decision 4)` under its status, 0017 and 0022, which each gain `Narrowed by 0030 (Decision 9)`; the roadmap's step 7 row, its sentence on import-linter, and its shell sketch, where `neolith check [--report]` becomes `neolith check <app> [<app> ...] --settings <module>`; and the README's list of what works, which gains the command.
- Neolith owns the resolution of import statements and the map from names to files. Its tests: one flagged and one admitted example for every row of the findings table; one refused value per row of the input table; every import form of Decision 3, with the edge it gives; fixtures for each literal dynamic import form (`import_module` with a keyword and a positional package, `__import__`, `import_string`, `include` with a string and a tuple), an assigned and a parameter `__import__`, which give no edge, and for each computed form that gives W101; each bare form of E109; a package `__init__.py` above a contract module that imports the app's internals; a models package that re-exports its models; a namespace package and a nested first-party directory in the map; a virtual environment inside the repository, which is skipped; W103 in a WSGI module and not in a `conftest.py`; for name resolution, a parameter that shadows an import, a loop target, two functions that import different `connect`s, a method under a class-level import, a comprehension target that shadows an import of its own scope (in a function and at module level), the generated product of Decision 3's binding forms, scopes, declarations and positions inside each module-level compound statement (`if`, `try`/`except`/`else`/`finally`, `with`, `for`/`else`, `while`/`else`, `match`), run under the interpreter, with the invariant on every fixture that each name the module's table marks `is_imported()` comes from an import the rule collected, an assignment expression in a list comprehension at module level and in a function under an import of the same name, a bare annotation and a `type` statement under an import, a type parameter that shadows an import, the `try`/`except ImportError` form of `include`, an import in a module-level `with`, `for`, `while` and `match` block after a top-level import of the same name from another module, under which the name is not followed, and `from <m> import *` after an import of the same name, under which the name is not followed; every way to bind and call each name of Decision 3's resolution (`from django.conf.urls import include`, a from-import of the module, of its package, an alias, an attribute chain, `import neolith.testing`, `from django.db.transaction import atomic`, `from django.db import connection as conn`, `using=DEFAULT_DB_ALIAS`, a bare `@non_atomic_requests`); E109's set compared with `django.db.transaction` on both versions; a module-level `return` and a 3,000-term `+` chain, the first E112 and the second no finding; a hosted app nested in another whose `__init__.py` imports its internals; an app installed in the user site directory; a differential test that compares the walk's edges with grimp's on Django's installed package. grimp joins the `test` dependency group, pinned, for that test only, with the one-line reason K5 asks for, and with an environment marker that limits it to the CPython versions it ships wheels for; where it is absent, the test is skipped with that reason. Further tests: a chain through a first-party module and one through a library module, which is not followed; a stale report-only entry; a query at import under both entries; on 6.1, a `JSONField` model on a SQLite path that does not exist, where under both entries no connection opens and no file is created; an internal error, which exits 2; the exit statuses; and `manage.py checkapps` and `neolith check` giving the same lines for phases 4 and 5 and the same summary for the same host. Each finding's test cites its requirement with the `spec` marker (T5).
- The functions cited agree between 5.2 and 6.1 except two: `run_checks`, whose 6.1 default of every alias is the reason `checkapps` sets `requires_system_checks = []`, and `django.db.transaction`, where 6.1 adds `savepoint_create`, which E109's set takes in because it is read from the installed module. With that, nothing here needs `neolith._compat`.
- Reading every file costs seconds on large projects. No speed is claimed (K10); a pull request that makes the walk faster, such as a per-file cache, brings its measurement.

## Open questions

1. **A ratchet inside a report-only app.** Decision 6 has none. If adopters find whole-app report-only too coarse, or regressions in apps under adoption costly, the candidate is a generated baseline: written by a command, never by hand, keyed so that a finding moved to another line still matches, failing on any finding not in it and on entries that match nothing, with a stated rule on who may regenerate it. Packwerk's `package_todo.yml` with `strict`, ArchUnit's `FreezingArchRule` and ESLint's bulk suppressions are the prior art. Hand-written per-import exemptions, as import-linter's `ignore_imports`, are the alternative, and are a second statement of the boundary. Either needs its own record.
2. **First-party code outside the hosted apps' and the settings module's directories.** Decision 3 follows chains only under those directories. A project whose shared code is installed into the interpreter's library directories is not followed. An input naming further first-party packages would close that, and would be one more thing to write.
3. **A machine-readable report.** JSON, or SARIF for code scanning annotations, would be a second form of every finding. The line form `<path>:<line>: <id> <message>` already matches the common CI problem-matcher pattern, so annotations in GitHub Actions need only a matcher file, not a second form of the message. Evidence from adopters' CI would help choose.
4. **Contract packages and `requires`.** Decision 2 lets any app import any contract package, as OVR-1 reads. Most compared tools keep a rule on declared dependencies apart from the rule on what is public: Packwerk's `enforce_dependencies` beside its former privacy checks, Spring Modulith's `allowedDependencies`, Tach's `depends_on` with `exact` for unused ones, and Nx's `depConstraints`. Whether an app should require a contract before importing its package, so that a type-only dependency is declared too, is not decided. A warning, not an error, for importing a contract package of a contract the app does not require would be a low-cost first step.
5. **Templates and URL names.** `{% load %}`, `{% include %}` and `reverse()` can reach another app (Decision 5). A pass over templates is possible, and is a parser of another language.
6. **Raw SQL.** Table names in SQL strings could be matched against other apps' tables. It would misfire on every string that happens to contain one, so it is left out.
7. **A host that holds only some apps.** Decision 1 judges only the apps of the host it builds. A check that reads the declarations of every app in a repository, without hosting them, would see boundaries to apps outside the host; it needs a way to find declarations that 0021 does not give (no module scan).
