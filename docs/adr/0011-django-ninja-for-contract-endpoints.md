# 0011. The host serves contract endpoints itself, from its root middleware, with no web framework

- **Status:** Proposed
- **Date:** 2026-11-03; amended 2026-11-18 for roadmap step 5 (#12)

## Context

Contracts are Pydantic-typed and published as OpenAPI ([0006](0006-contracts-are-typed-and-published-as-openapi.md)). Over HTTP, a provider's host serves one endpoint per action, `POST /<name>/v<N>/<action>`, and the OpenAPI 3.1 document at `GET /.well-known/neolith/openapi.json` (spec 03, HTTP-2). This record decides what serves them. The earlier text of this record chose django-ninja. It was written before roadmap steps 2 to 4, which settled most of what an endpoint does. Since then:

1. **The package writes and reads every value itself.** [0007](0007-in-process-transport-serializes.md) Decision 1 dumps a value with the declared type's schema-built serializer, never with a record's own methods. Decision 3 has the receiver run the description check, then the declared type's validator, and over a network both sides run the description check. `neolith._crossing.Codec` does this, from the core schema the description was written from. Its `read` runs the validator only, which is what an in-process receiver needs.
2. **A receiver reads JSON text, never a parsed value.** [0020](0020-wire-forms-pydantic-writes-otherwise-are-neolith-annotated-types.md), Consequences: `Binary` is read from JSON text only. A receiver validates the body's text with `validate_json`, "never a value parsed from it first (`json.loads`, a framework's body parser), which refuses every `Binary` value". The same text binds "the HTTP endpoints of roadmap step 5 too, whatever library serves them". The endpoint also checks CON-42 on its own.
3. **The package already has a neutral description.** `Contract.describe()` returns each action's idempotency and the JSON Schema 2020-12 of its request, reply and declared error details, under `$defs` (`src/neolith/_contracts.py`). Its integers carry the range of [0019](0019-wire-encodings-of-the-portable-forms.md). Pydantic's own schema does not. Probe, Pydantic 2.14.3: for a field `qty: int`, `describe()` gives `{"type": "integer", "minimum": -9007199254740991, "maximum": 9007199254740991}`, and `model_json_schema()` gives `{"title": "Qty", "type": "integer"}`. CON-9 says the projection is "derived from the contract, never hand-written", and CON-34 requires the description to state each range.
4. **The provider's side already exists, shaped for one transport.** The in-process transport takes an action, the request's JSON text and a `Sent` context, and returns the reply's text or a `Failure` carrying kind, message and detail text (`InProcess.call`, `src/neolith/_connector.py`). It runs the provider's steps of [0017](0017-call-context-explicit-at-the-action-ambient-for-propagation.md) Decision 9 from step 2, and the rules of [0008](0008-typed-contract-errors-in-both-modes.md) on what an action may deliver. Four of its details fit only the in-process case: it counts the deadline from when `call` is entered (`arrived = _context.now()`); `Sent.idempotency_key` is a `str`, so it cannot say that a call arrived without a key; `_context.received` decodes the principal inside `_serve`, which turns any exception there into `internal`; and it reads the request with `Codec.read`, without the description check.
5. **Every failure on a contract path carries a neolith error body.** 0008 Decision 8 says this includes a request that fails validation and a failure of the host itself, "so the framework's own error responses never reach a caller". Spec 03 says the host authenticates the calling app "before it reads the request body or any call-context header", and then runs its other checks "in the order of ADR 0017 Decision 9", whose first provider step is "The calling app is authenticated (`unauthenticated`)."
6. **The root middleware is first and checked.** [0022](0022-the-app-host-builds-settings-and-checks-before-it-serves.md) Decision 6 makes `neolith.middleware.RootMiddleware` the first entry of `MIDDLEWARE`, listed once, and its constructor boots the host (Decision 7), which imports `ROOT_URLCONF`. 0017 Decision 4 lists the provider side of each transport as a root of its own, apart from "the host's handling of ordinary Django requests". 0022 open question 2 leaves to this step whether the host builds the URLconf or the deployer includes the host's URLs.
7. **Spec 01 already keeps names to ASCII.** CON-10 makes an identity lowercase ASCII segments, and CON-20 makes a record or enum name an ASCII letter followed by ASCII letters, digits or underscores; `_portable.register` refuses any other name when the contract is declared.

Each ASGI request therefore runs its thread-sensitive code on a thread of its own, and requests run concurrently.
  - *The body under ASGI.* `ASGIHandler.handle` awaits `read_body` before it builds the request or sends `request_started` (line 174 in 5.2.19, 181 in 6.1.3). `read_body` writes every chunk to a `SpooledTemporaryFile(max_size=FILE_UPLOAD_MAX_MEMORY_SIZE)`, which rolls over to disk, with no bound on the total. `HttpRequest.body` checks `DATA_UPLOAD_MAX_MEMORY_SIZE` later, against `Content-Length` and then against the size actually received (`http/request.py`).
  - *The body under WSGI.* `WSGIRequest` wraps `wsgi.input` in a `LimitedStream` of `Content-Length` bytes, and of 0 bytes when the header is absent (`core/handlers/wsgi.py`), so a chunked body with no `Content-Length` reads as empty. A read that fails raises `UnreadablePostError`.
  - *Headers.* `ASGIRequest` drops every header with an underscore in its name and joins repeated headers with `,` (`core/handlers/asgi.py`).
  - *Paths.* `path_info` is the path with `SCRIPT_NAME` removed, and `path` is the full path (`core/handlers/asgi.py`, lines 54 to 60; `core/handlers/wsgi.py`). Both are percent-decoded by the server: `wsgiref.simple_server` sets `PATH_INFO` to `urllib.parse.unquote(path, 'iso-8859-1')` (line 85, Python 3.13), and ASGI's `scope["path"]` is decoded. `/inventory%2Fv1/res%65rve` reaches Django as `/inventory/v1/reserve`.
  - *Response logging.* `BaseHandler.get_response` calls `log_response` for every response with status 400 or above, outside the middleware chain (`core/handlers/base.py`). `log_response` logs a 5xx at `ERROR` and a 4xx at `WARNING` on `django.request`, with the request attached, and skips a response whose `_has_been_logged` is true (`utils/log.py`). `DEFAULT_LOGGING` sends `django` to `mail_admins` at `ERROR` when `DEBUG` is false, and `AdminEmailHandler` renders `technical_500.txt`, which lists `META`. The filter on `META` hides names that match `API|AUTH|TOKEN|KEY|SECRET|PASS|SIGNATURE|HTTP_COOKIE` (`views/debug.py`, line 115), so `HTTP_AUTHORIZATION` and `HTTP_IDEMPOTENCY_KEY` are hidden and `HTTP_NEOLITH_PRINCIPAL` is not.
  - *Disconnects under ASGI.* When the client disconnects, `ASGIHandler.handle` cancels the request's task and sends `request_finished` (5.2.19, after line 228); a sync function already running on its thread runs on.
  - *Other.* `request_started` and `request_finished` run `close_old_connections` (`db/__init__.py`) whatever the middleware does. `LoginRequiredMiddleware` redirects any view not marked `login_not_required` (`contrib/auth/middleware.py`, from Django 5.1). `SecurityMiddleware` redirects to HTTPS when `SECURE_SSL_REDIRECT` is true, `request.is_secure()` is false and no `SECURE_REDIRECT_EXEMPT` pattern matches the path (`middleware/security.py`).
- **Prior art for a middleware that serves its own paths.** WhiteNoise 6.12.0 (MIT) serves a file from `__call__`, before `get_response`, when `request.path_info` names one (`whitenoise/middleware.py`). Django's `FlatpageFallbackMiddleware` and `RedirectFallbackMiddleware` answer from middleware too, after the view.
- **Prior art for RPC over HTTP.** Twirp and Connect serve one `POST` endpoint per method with a JSON body and an error body of fixed shape. Twirp's generated `ServeHTTP` answers every path under its service prefix itself, and a path that names no method gets `bad_route` (404) (`example/service.twirp.go`; Twirp spec v7). connect-go v1.19.1 admits `application/json` and `application/json; charset=utf-8`, parsing with `mime.ParseMediaType` and lower-casing the charset value (`codec.go`; `protocol.go`, `canonicalizeContentTypeSlow`), and answers a method it does not serve with 405 and an unsupported codec with 415 (`handler.go`).

## Options

1. **Django REST framework.** Familiar to most of the audience: about 49% in the 2025 Django survey. Its parser hands on a parsed value, which 0020 rules out for `Binary`. Its serializers are not Pydantic, so the contract types would need a translation layer. Its views are sync only. OpenAPI 3.1 needs a further package.
2. **django-ninja.** Pydantic-native, typed, sync and async, and its dependencies are already the package's. Each part an endpoint would use is one that neolith already has and has to keep: the body parser, the reply writer, the schema writer and the error bodies. Each would be replaced or bypassed, leaving routing and method dispatch.
3. **The host's own layer on Django's request and response objects.** It reuses the codec, the description and the provider side the package already has. It adds no dependency. Routing, the admitted request forms and the error bodies are then the package's to write and test.

## Decision

Option 3. The endpoint layer is part of the host. It adds no runtime dependency (CONTRIBUTING K5) and no public API: an app author writes contracts, and a deployer writes nothing for it. Adopters keep using DRF or django-ninja for their own APIs, which this record does not touch.

### The admitted set

**Which requests the host answers.** The host compares `request.path`, the full path with any `SCRIPT_NAME`, as the server percent-decoded it, the same text Django routes on. Paths are compared code point by code point. A path is *owned* when it starts with `/<name>/v<N>/` for a contract version the host provides, or with `/.well-known/neolith/`. The host passes every request on a path it does not own to the rest of the middleware chain unchanged. On an owned path:

- **Host first.** The host calls `request.get_host()`. A Host outside `ALLOWED_HOSTS` raises `DisallowedHost`, which the host lets through, so Django answers it as it answers any such request: a 400 from the deployer's `handler400`, logged on `django.security.DisallowedHost`. A request that is not addressed to this host is on none of its contract paths, so no step of 0017 Decision 9 applies to it and it carries no neolith error body.
- **Contract path.** The path is exactly `/<name>/v<N>/<action>` for an action of that version (spec 03).
- **Well-known path.** The path is exactly `/.well-known/neolith/openapi.json` or `/.well-known/neolith/health`.
- **Any other owned path**, such as a misspelt action, an action from a newer minor version, or a trailing slash, gets 404 with an empty body, whatever its method. It is not a contract path, so spec 03 gives it no neolith error body, and a connector maps it to `unavailable`. It never reaches the deployer's middleware or URLconf (Decision 2).

On a contract path, the host checks each input in the order of the table and stops at the first that fails. The order is 0017 Decision 9's provider order, and the *Step* column names its step. The method, the query and the scheme are checked within step 3, before the neolith headers, and the body's headers within step 5, before the body: this adds checks inside two steps and moves none, so 0017's text is not edited. The calling app is authenticated before the host looks at the method, the query, any call-context header or the body. Rows 1, 2 and 6 belong to 0027, the step 5 record on the calling app over HTTP, which owns the forms of `Authorization` and of the neolith headers, the handling of repeated fields, underscores and unknown `neolith-` headers, and their messages. This record names those rows and does not decide them a second time. No refusal message shows a value that arrived.

A `Content-Type` or `Content-Encoding` sent twice reaches Django as one value joined with `,` (`ASGIRequest` joins them, and WSGI servers do the same, as RFC 9110 section 5.3 allows), and the joined value fails row 9 or 10. 0027 Decision 6 gives the same outcome for its headers, and says what an underscore in a header's name does.

**Headers the table does not name** are ignored, as RFC 9110 section 5.1 asks of recipients and as CON-6 ignores an unknown field. That includes a header whose name starts with `neolith-` and that spec 03 does not define: 0027 Decision 6 ignores it and keeps the prefix reserved to spec 03, and its open question 1 keeps the trade-off with headers a provider must understand visible. This record follows it.

**Two deliberate exceptions to one form per input.**

- *Row 9* admits several spellings of one media type. RFC 8259 (section 11) defines no `charset` parameter for `application/json`, and says that adding one "really has no effect on compliant recipients". Yet .NET's `JsonContent` sends `application/json; charset=utf-8` by default (`JsonHelpers.DefaultMediaType`, dotnet/runtime), and connect-go admits the same two media types, with the charset value in any case. RFC 9110 sections 5.6.6 and 8.3.1 make OWS around `;` and a quoted value equivalent to the plain form, so the admitted spellings are the ones HTTP treats as one value. Refusing them would turn away common non-Python callers, and 0006 expects such callers to dock as detached peers. A neolith caller sends exactly `application/json`.
- *The path* is compared after the server's percent-decoding, as Django routes, so `/inventory%2Fv1/res%65rve` is the contract path `/inventory/v1/reserve`. Comparing the raw path was weighed: ASGI has `raw_path`, but WSGI has no standard raw path, so the comparison would differ between servers. The documentation warns that a proxy rule for an owned path matches the decoded path.

**Status of the refusals.** Connect answers rows 3, 9 and 10 with 405, 415 and 415, with no body, and Twirp answers them with `bad_route` (404). Neolith answers them with 400 and a neolith error body, because spec 03 ties the status to the kind and a connector reads the kind from the body only, so every failure on a contract path is one of spec 03's kinds. The same reason gives row 12 `invalid_argument` rather than HTTP's 413 or Connect's `resource_exhausted`: spec 03 has no such kind. The headers that advertise what is admitted (`Allow`, `Accept-Post`, `Accept-Encoding`) are borrowed, since RFC 9110 lets them go with any status.

**A well-known path** admits `GET` and `HEAD`, with no query. `HEAD` gets the status and headers of `GET` and no body (RFC 9110, section 9.1). Any other method gets 405 with `Allow: GET, HEAD` and an empty body, and a query gets 400 with an empty body. A well-known path is not a contract path, so neither carries a neolith error body (spec 03, Errors).

### 1. No web framework: the endpoint layer is the host's, on Django's request and response objects

The layer is a small part of the host. It parses the request line and the headers, calls the backends, builds the call's context, hands the action, the request's text and the context to the provider side (Decision 3), and writes the response (Decision 4). It uses `HttpRequest`, `HttpResponse`, `ALLOWED_HOSTS`, `DATA_UPLOAD_MAX_MEMORY_SIZE` and the `SECURE_*` settings it reads as Django defines them. The shape, one `POST` endpoint per action with a JSON body and an error body of fixed shape, is the one Twirp and Connect use.

Alternatives weighed:

- **django-ninja**, as the earlier text of this record chose. Its licence (MIT), typing, sync and async support and dependencies all meet K5. Its maintenance is active. The difficulty is fit, not quality. Its body parser hands on a parsed value, which 0020 rules out. Its reply writer would bypass 0007 Decision 1's sender. Its schemas come from `model_json_schema`, a second writer beside the description, and state less than the provider enforces: fact 3's integer range, for one. Its error bodies use `detail`, which 0008 Decision 8 renamed `data` to avoid. Its `DEBUG` handler sends a traceback, which 0008 Decision 3 forbids. Using it would mean replacing its parser, renderer, exception handlers and schema generator, and turning off its docs page and its 405 response. What would remain is URL routing and method dispatch: two dictionary lookups. That would add a dependency that every adopter installs and must keep compatible, and a minor-version floor that an adopter's own ninja API would have to share. Principle 13 asks the package to use what exists. Here the work that exists elsewhere is the work neolith's wire rules already do differently, on purpose.
- **Django REST framework.** BSD-3-Clause, maintained and widely known, with Django as its only dependency. It has no async views, no inline types, and a parser that hands on a parsed value. Its OpenAPI generator writes 3.0.2 and is deprecated. Its serializers would need a translation layer from the contract types. It fits an adopter's own API better than a generated one.
- **A thin layer on Starlette or another ASGI framework, mounted beside Django.** Fast, and async-native. It would bypass Django's handler, so `request_started`, `request_finished` and their connection handling would not run around an action that uses the ORM. It would also not run under WSGI, which 0022 Decision 9's `neolith run` serves.

Follows principles 10 (*Django-native*), 11 (*specification over implementation*) and 12 (*small core*).

### 2. The root middleware answers every owned path, ahead of the rest of the chain

For a request on an owned path, `RootMiddleware.__call__` answers the request itself and never calls `get_response`. It opens no request root: the provider side opens the call's root after its checks (0017 Decision 4, the first entry point). For every other request, the middleware behaves exactly as it does today. The table of owned prefixes and contract paths is built at set-up, from the actions of each contract version the host provides, and held on the set-up's `Host` table, so an `override_settings` that sets the host up again brings its own table. `ROOT_URLCONF` stays the deployer's, unchanged (0022 Decision 2). The deployer adds no URL pattern. Once Accepted, this answers 0022 open question 2.

The host owns each provided version's whole prefix, as Twirp owns its service prefix, so that a path under it that names no action gets the same 404 on every host. Otherwise such a path would reach the deployer's chain, and the caller's outcome would depend on it: a `CsrfViewMiddleware` 403 or a `LoginRequiredMiddleware` redirect maps to `unavailable`, and a catch-all view's 200 page maps to `internal`.

**Boot warns about a deployer URL that the host shadows.** Boot already imports `ROOT_URLCONF` (0022 Decision 7). It then resolves each contract path, and each provided prefix `/<name>/v<N>/`, against the deployer's URLconf, and for each that resolves it emits a warning check, `neolith.W003` (numbered when the code lands), that names the contract version, the path and the URL pattern, and says the host answers that path. It is a warning, not a refusal, because a catch-all pattern, such as one serving a single-page app, resolves every path, and refusing it would stop common deployments for a shadowing they may intend. A deployer silences it with `SILENCED_SYSTEM_CHECKS` (K2). The check costs one `resolve()` per action and per version, once per process.

Alternatives weighed:

- **The deployer includes the host's URLs**, as `path("", include("neolith.urls"))`, the way the admin site is included. It is the most familiar form in Django. But the whole of the deployer's middleware then runs before a contract call. `CsrfViewMiddleware` and `LoginRequiredMiddleware` would each need a mark on the view, `csrf_exempt` and `login_not_required`. Any other middleware could answer a contract path with its own redirect or error page, which 0008 Decision 8 rules out. It could also parse the body before the calling app is authenticated, which spec 03 rules out. `RootMiddleware` would open a request root for a request that is not an ordinary one, and the provider side would then open the call's root inside it. A missing or misplaced `include()` would also be one more misconfiguration to detect at Boot, and the well-known path must sit at the origin's root (RFC 8615), wherever the deployer includes the rest.
- **The host builds the URLconf.** One form, with nothing to forget. But it takes `ROOT_URLCONF` from the deployer, which 0022 Decision 2 leaves with the deployer, and it still runs the deployer's middleware before each call.
- **A second middleware class** for contract paths, listed after `RootMiddleware`. Its position would need checking like the first's (0022 Decision 6), and every middleware listed between the two would run before a call. The first entry already exists and is already checked.
- **Answer exact contract paths only**, and pass the rest of each prefix to the deployer. It shadows fewer deployer URLs, but leaves the outcome of a misspelt or newer action to the deployer's chain, as above.

What the deployer's middleware does for ordinary requests (sessions, CSRF, authentication, locale, security headers, logging) does not run for a contract call. A contract call is the transport, not a page, and its checks are those of spec 03. The settings whose intent bears on a call are read directly: `ALLOWED_HOSTS` on every owned path, and `SECURE_SSL_REDIRECT` in row 5. Django's handler still sends `request_started` and `request_finished` around the call, so database connections are handled as for any request. Prior art serves files the same way (WhiteNoise, fact above).

### 3. One provider side for both transports, entered after step 3

The in-process transport and the HTTP endpoint share the provider side from 0017 Decision 9's step 4 on: the deadline, the request's receive check, the action in its own scope, and the rules on what an action may deliver (0008 Decisions 1 to 4), including the check of the deadline again when the action ends, as `InProcess.call` does today. Each transport runs steps 1 to 3 itself. In-process that is `InProcess._refusal`, as today. Over HTTP the endpoint authenticates the calling app (row 1), runs the same `_refusal` function for the allow-list (row 2, as 0027 Decision 5 says), and then reads the request line and the neolith headers (rows 3 to 7). The allow-list therefore runs once per call on each transport.

Fact 4's details become the shared side's interface. It takes from the transport:

- the deadline, already counted from when the call arrived: in-process, when `call` is entered; over HTTP, when the endpoint is entered, before the first caller backend runs and before any thread hop (TRN-36, 0027 Decision 1). Under ASGI the server has already received the body by then (Consequences);
- the idempotency key, or none, since a call that arrives over HTTP without `Idempotency-Key` has no key (spec 03), so `Sent.idempotency_key` becomes optional;
- the principal the transport has already read, so a malformed `Neolith-Principal` is the endpoint's `invalid_argument` at row 6, never `internal`;
- the receiver kind, which turns on the network receive check of 0007 Decision 3: CON-42 on the body's text, the description check and CON-40, before the declared type's validator reads the same text.

Alternative weighed: **a second provider side written for HTTP.** It would let the two transports drift apart in exactly the place principle 5 asks them to agree. Sharing one side means a conformance test that passes in-process exercises the same code over HTTP, from step 4 of 0017's order on.

### 4. What the host sends back

- **A reply:** status 200, `Content-Type: application/json`, and the body is the text the sender wrote (0007 Decision 1), byte for byte. It is never parsed and written again.
- **An empty reply:** status 204 with no body and no `Content-Type` (RFC 9110, section 15.3.5). A connector takes 200 for an action with an empty reply, and 204 for any other action, as a reply that is not valid, so `internal` (TRN-18).
- **An error:** the status of its kind (spec 03), `Content-Type: application/json`, and the body `{"kind":"<kind>","message":"<text>"}`, with `"data":<detail>` added for a declared kind. The detail's text, as the sender wrote it, is placed in the body unchanged. A 401 also carries exactly `WWW-Authenticate: Bearer realm="neolith"` (0027 Decision 8). A refusal in rows 3, 9 and 10 also carries `Allow: POST`, `Accept-Post: application/json` and `Accept-Encoding: identity` respectively.

The host sets no other header. Alternatives weighed for the empty reply: **200 with `null`**, or **200 with `{}`**, as Twirp and Connect send an empty message. `null` is a value that the description does not describe, since CON-16 leaves an empty reply out. `{}` would look like a record with no fields, which a later version could fill. 204 says there is no content, in HTTP's own terms.

### 5. Every failure on a contract path is a neolith error body, and each response is logged once by the host

The endpoint catches every `Exception` that comes out of its own code, a backend or the provider side, and answers `internal`: the fixed message with the trace identifier, with the cause logged (0008 Decision 3). An exception that is not an `Exception`, such as cancellation, propagates (0008 Decision 3). `RequestDataTooBig` and `UnreadablePostError` are row 12's refusals, not `internal`: a body too large, or one that ended early because the caller went away or sent a wrong `Content-Length`, is the caller's input. Because nothing else in the middleware chain runs for an owned path (Decision 2), no response from Django or from the deployer's middleware can reach a caller, apart from the handler's own failures before the first middleware runs and the `DisallowedHost` answer of the admitted set.

Django's handler would otherwise log every 4xx and 5xx contract response through `log_response`, with the request attached. With the default logging, a 500, 503 or 504 then mails the request's `META` to `ADMINS`, and the debug filter does not hide `HTTP_NEOLITH_PRINCIPAL`, the end user's data, which 0027 keeps out of every output. So the endpoint logs each contract response itself and marks it logged, with `response._has_been_logged = True`, which makes `log_response` skip it:

- one line per response on `neolith.calls`, with the contract version, the action, the status, the kind and the trace identifier, and, for a refusal at steps 1 to 3, the fields 0027 Decision 8 names, with no request attached, so no handler can render `META`;
- `WARNING` for every refusal and failure kind except `internal`, and `INFO` for a reply and for a declared kind, which is an outcome the contract describes;
- `internal`'s cause is logged at `ERROR` once, by whichever of the endpoint and the provider side caught it, as 0008 Decision 3 asks, again with no request attached. So only a failure of the host itself reaches `mail_admins`, and `timeout` and `unavailable` do not. For any report that other code makes with the request, 0027 Decision 3 sets a reporter filter on contract paths that hides every `HTTP_NEOLITH_` key.

`_has_been_logged` is private to Django. It has the same meaning in 5.2.19 and 6.1.3 (`utils/log.py`), the host sets it in one place, and a test at each end of the [0012](0012-supported-python-and-django-versions.md) matrix asserts that `log_response` skips a marked response, so a change in Django fails the version tests first. Alternative weighed: **leave `log_response` alone and document a filter on `django.request` for contract paths.** It touches nothing private, but the default would mail the end user's data until a deployer adds the filter, which K9 rules out.

### 6. Sync and async

The endpoint runs in the mode the middleware runs in (0022 Decision 6). Actions are synchronous in this version (`_contracts.py` refuses a coroutine function). In the async mode, the endpoint runs the provider side through `sync_to_async(..., thread_sensitive=True)`, as Django runs a sync view, and as django-ninja runs a sync operation. Django enters a `ThreadSensitiveContext` for each ASGI request (fact above), so each contract call runs on a thread of its own, as a sync view does, and calls run concurrently under ASGI as under a threaded WSGI server. Database connections stay per thread, as Django keeps them.

Alternative weighed: **`thread_sensitive=False`**, which would run the provider side on the event loop's shared thread pool instead of the request's own thread. It adds no concurrency that the request's own thread does not already give, and it would differ from how Django runs a sync view's database work. 0022 fact 6 records the limits on database access while an event loop runs. Async actions can come later, under a record of their own.

### 7. The OpenAPI document is projected from the description, built at set-up and served as fixed bytes

Set-up builds one document for every contract version the host provides, from `Contract.describe()` only, and keeps its JSON text on the set-up's `Host` table. `GET /.well-known/neolith/openapi.json` returns those bytes, status 200, with `Content-Type: application/json`. The document is served without authentication, as spec 03's HTTP-2 places it. Its content is fixed as follows:

- **Top level:** `"openapi": "3.1.2"`, and `"jsonSchemaDialect": "https://json-schema.org/draft/2020-12/schema"`, the dialect the description declares. Every schema is then read as plain JSON Schema 2020-12, not the OpenAPI base dialect. `info` holds `"title": "neolith contracts"` and, as `version`, the version of the specification the host conforms to (spec README). There is no `servers` member, so the server is `/` relative to the document's location (OpenAPI 3.1.2, section 4.8.1.1), which is the origin's root, where 0.1 serves (the admitted set compares the full path).
- **Paths:** contract versions are ordered by identity, code point by code point, and actions are kept in declaration order. Each action is `"/<name>/v<N>/<action>": {"post": {...}}`, with:
  - `operationId` set to `<name>.v<N>.<action>`, which is unique because identities and action names are (CON-10, CON-12);
  - `tags` set to `["<name>.v<N>"]`;
  - `x-neolith-idempotent`, `true` or `false`, carrying CON-16's idempotency, which OpenAPI has no field for;
  - `parameters` referencing the shared header parameters below;
  - `requestBody`, required, with `application/json` and a reference to the request record;
  - `responses`: `200` with the reply record, or `204` for an empty reply; one shared response per standard kind, keyed by its status; and `422`, only when the action declares kinds, whose schema is a `oneOf` with one object per declared kind: `kind` as a `const`, `message` a string, `data` a reference to the detail record.
- **Components:** each record and enum of a contract's `$defs` is copied unchanged under `components.schemas`, keyed `<name>.v<N>.<Record>`. Two versions of one contract often share record names, so the key carries the identity. Each `$ref` of the form `#/$defs/<Record>` is rewritten to `#/components/schemas/<name>.v<N>.<Record>`, and nothing else in a schema changes. Every key matches OpenAPI's `^[a-zA-Z0-9\.\-_]+$` (section 4.8.7.1), because CON-10 and CON-20 keep identities and record names to ASCII letters, digits, `_` and `.` (fact 7). `components.securitySchemes` holds one `http` scheme with `scheme: bearer`, which the document's top-level `security` requires, matching spec 03's challenge. `components.parameters` describes `Neolith-Principal`, `Neolith-Timeout`, `Idempotency-Key`, `traceparent` and `tracestate` as optional header parameters, each with spec 03's pattern or length where it has one. `Authorization` and `Content-Type` are not parameters, since OpenAPI ignores header parameters with those names (section 4.8.12.2.1).

The text is written once, with `json.dumps(..., ensure_ascii=False, separators=(",", ":"))`, so that equal hosts serve equal bytes. `HEAD` on the path gets the same headers and no body.

`GET /.well-known/neolith/health` returns 200 with an empty body. A process answers it only once Boot has passed (0022 Decision 7), which is spec 03's "can serve its contracts". The path means *ready*, not merely *live*. What it answers during Drain is open question 6.

Alternatives weighed:

- **ninja's or Pydantic's schema generation.** A second writer would drift from the description that the checker enforces (0007 Decision 2), as fact 3 shows.
- **One document per contract version**, at `/.well-known/neolith/<name>.v<N>/openapi.json`. Smaller documents, but spec 03 fixes one location.
- **`servers` with a relative URL such as `../../`**, which would also be correct under a path prefix. Tools resolve relative servers unevenly (section 4.7), and 0.1 serves at the origin's root (open question 1).
- **Records under one shared `$defs` member per contract**, referenced as `#/components/schemas/<name>.v<N>/$defs/<Record>`. It is valid OpenAPI 3.1, but many tools list only the top-level component names.
- **OpenAPI 3.2.0**, released with 3.1.2 on 2025-09-19. Spec 03's HTTP-2 names 3.1, and tooling support for 3.2 is still uneven. 3.1.2 is a patch release of 3.1 that changes no structure.
- **RFC 9727's `/.well-known/api-catalog`**, a linkset whose `service-desc` relation points at an OpenAPI document, so generic tooling can find it. A host could serve it beside this path, linking to `/.well-known/neolith/openapi.json`. That is additive and can come later without changing this one.

## Consequences

- No runtime dependency is added. `pyproject.toml` is unchanged, and when this record is accepted the roadmap's "provider endpoints via django-ninja" becomes "provider endpoints served by the host".
- An app author and a deployer write nothing for contract endpoints. The host answers every path under a provided version's prefix and under `/.well-known/neolith/`, for every method. A deployer URL there is never reached, Boot warns about each one it finds (Decision 2), and the documentation says so.
- The deployer's middleware does not run for a contract call: HSTS, request logging and metrics middleware among it. `ALLOWED_HOSTS` and `SECURE_SSL_REDIRECT` keep their meaning, because the host reads them itself. With `SECURE_SSL_REDIRECT` true, a call over plain HTTP fails visibly with `invalid_argument` (row 5); its token has been sent by then, but the caller learns and stops. TLS itself is the server's or the proxy's job, and the documentation says this next to the shared-secret warning of spec 03. `ATOMIC_REQUESTS`, which Django applies to resolved views, does not wrap an action: an action that wants a transaction opens one on its own app's alias ([0009](0009-one-database-alias-per-app.md)).
- The order on a contract path is 0017 Decision 9's, unchanged: a call with no credential gets `unauthenticated` whatever its method, query or body. The method, the query and the scheme are part of step 3, before the neolith headers.
- Under ASGI, Django receives the whole body before any middleware runs (fact above), so an unauthenticated caller's body has already arrived, possibly spooled to disk, when the host refuses it. Spec 03's rule holds in the sense that the host neither parses nor validates the body, nor reads a call-context header, before authentication. The bound on what arrives belongs to the ASGI server or the proxy, and the documentation names it, such as nginx's `client_max_body_size`. Under WSGI, the host refuses an unauthenticated call without reading the body, and row 12 refuses on `Content-Length` before reading.
- A request without `Content-Length` is refused on every server (row 11), so a chunked body gets the same outcome under ASGI, which would receive it, and WSGI, which would read it as empty. An HTTP/2 client that omits `Content-Length` is refused too. A neolith caller sends it.
- The path is compared after percent-decoding, so a proxy rule written against raw paths can miss a spelling of an owned path. The documentation says to match decoded paths.
- A host under a `SCRIPT_NAME` prefix serves no contract path in 0.1: the full path then starts with the prefix, matches nothing the host owns, and reaches the deployer's chain, so a caller sees `unavailable`, or `internal` where a catch-all view answers with a success status (Decision 2), rather than a document that points to the wrong place. This matches 0014's `url`, an origin with no path.
- In 0.1 a provider's host has no maximum budget of its own. A call that arrives without `Neolith-Timeout` has no deadline (0017 Decision 3), so a slow or hung action can hold a worker for as long as it runs. Under ASGI, a caller that disconnects cancels the request's task, and Django sends `request_finished`, while the action runs on in its thread.
- The in-process transport's provider side becomes shared code from 0017's step 4 on, with the interface of Decision 3. Its in-process behaviour does not change, and the HTTP endpoint is tested through the same contract suite (T2), over a live server on the local machine (T3). Calls reach it through the private `over_http` seam of [0014](0014-pluggable-connector-transports.md) Decision 6, as amended for step 5, since a live server in one process serves only the providers its own host holds.
- Contract responses are logged by the host, once each, on `neolith.calls` (Decision 5). Only `internal` reaches `ERROR`, and no log record from a contract response carries the request.
- The document is checked in tests against the OpenAPI Initiative's published 3.1 schema, with `jsonschema`, which is already a test dependency. The existing round-trip property test (CON-16) can run against the document's component schemas too.
- Spec 03 changes with the step 5 pull request that builds the endpoints, which gives these rules requirement IDs and tests (P5): the host authenticates before it parses or validates the body or reads any call-context header; a request not addressed to this host carries no neolith error body; a path under a provided version that names no action gets 404 with none; the request line (method `POST`, empty query) and the body's headers (`Content-Type`, no `Content-Encoding`, `Content-Length` present, an optional body limit); the reply forms, 200 and 204; headers spec 03 does not name are ignored; HTTP-2's document structure; the well-known paths answer GET and HEAD, and health means ready. Spec 06 gains a conformance test per row. `ALLOWED_HOSTS`, `SECURE_SSL_REDIRECT`, `DATA_UPLOAD_MAX_MEMORY_SIZE`, `neolith.W003`, the logged mark and percent-decoding are django-neolith's, in its documentation (P2).
- `docs/django-host.md` gains a section on owned paths, the Boot warning, the decoded-path note for proxies, the ASGI body bound, and the logging of contract responses. 0022's open question 2 is answered once this record is Accepted.

## Open questions

1. **A host under a path prefix** (`SCRIPT_NAME`). The well-known path belongs at the origin's root (RFC 8615), and the document's default server is the root. A deployment behind a prefix would need both to move, together with 0014's `url` row. FastAPI's form is the likely one: when a prefix is set, the document gains `servers: [{"url": <prefix>}]`, built per request.
2. **Hooks for contract calls.** Observability is the likely need: metrics or access logs that the deployer's middleware gives ordinary requests. Twirp's server hooks give a candidate shape: received, routed (after authentication), reply prepared, error (with its kind) and sent, which Django signals or a `NEOLITH` hook list could carry. Adopters' needs would settle the form.
3. **Registering the well-known name.** RFC 8615 section 3 asks that a new well-known URI be registered; a specification outside a standards body registers it as provisional. Spec 03 would be the specification cited, and the request to IANA is a task outside the repository, before 1.0.
4. **Access to the document.** It is served to anyone who can reach the host and passes `ALLOWED_HOSTS`. A deployer who wants it private can block the path at a proxy, matching the decoded path. A host setting to require a calling app's credential is possible later, and it would change HTTP-2's reading.
5. **A body limit per contract.** Row 12 uses Django's process-wide limit. A contract with large `Binary` fields might want its own; 0019 notes a validator that runs out of stack on about 4 MB of bytes text.
6. **Drain, health and a host maximum for inbound calls.** 0022 open question 13 bounds Drain by the host's maximum budget, and 0.1 has none (Consequences), so a key for it needs a record of its own, as 0022 open question 13 says of giving a call with no deadline one. Under `neolith run`, 0025 counts a contract call from its request line like any request. Under ASGI, a disconnected caller's action runs on after `request_finished`, so counting by Django's signals would end too early. The health path could also answer 503 once Drain begins, as Kubernetes' `readyz` does, so a load balancer stops routing before connections close; under another server the host cannot tell Drain from a quiet moment (0022 open question 9).
7. **An older provider from one that is down.** A path under a provided version that names no action gets 404 and maps to `unavailable`, the kind a connector may retry (TRN-8). gRPC and Connect keep `unimplemented` apart, so version skew is not retried. Spec 03 has no such kind; adding one is a change to spec 01's kinds.
8. **An early refusal while the body is still arriving.** Under WSGI the host refuses an unauthenticated call without reading its body (Consequences). A caller still writing a large body may then meet a reset before it reads the refusal, and report `unavailable` (0028, the HTTP client record). Reading or draining the rest of the body before closing, as servers' lingering close does, would let the caller read the refusal, at the cost of reading what an unauthenticated caller sent.
