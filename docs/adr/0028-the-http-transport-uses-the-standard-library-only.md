# 0028. The HTTP transport calls a provider over the standard library's sockets and TLS, with a strict HTTP/1.1 reader of its own, under one deadline for every blocking step, and adds no runtime dependency

- **Status:** Accepted
- Narrowed by [0032](0032-the-conformance-suite-runs-each-case-once-per-transport.md) (Decision 5)
- Narrowed by [0031](0031-a-contract-version-is-routed-by-single-unless-local-first-is-named.md) (Decision 5)
- **Date:** 2026-11-18

## Context

Roadmap step 5 (#12) delivers the "connector over httpx". The roadmap names httpx as a working assumption, and K5 asks for an Accepted record before any runtime dependency lands, because "every dependency becomes a dependency of every adopter". This record chooses the HTTP client that the HTTP transport uses to carry a call to a remote provider, and fixes what that client sends, accepts, reads from its environment and never does.

Much is already fixed, and this record builds on it:

- **Spec 02.** TRN-3: every failure maps to a standard kind, and no transport exception reaches the caller. TRN-4 and TRN-38: a call whose deadline passes fails with `timeout`, and "over a network the caller stops waiting at its deadline". TRN-27 to TRN-29: the deadline crosses as a budget, "the time that remains when the call is sent", in whole milliseconds rounded down, a call whose budget is under 1 ms is not sent, and a budget above 9999999999 counts as that. TRN-36: the provider counts its deadline "from the budget when the call arrived". TRN-17: under `single` a call is sent at most once. TRN-8: a retry only for an idempotent action, only on `unavailable`, only within the deadline. Spec 00, as it reads since #93: "A nested call's deadline, as the caller derives it ([02](../../spec/02-transports.md), TRN-27), is never later than its parent's. The nested call's provider counts its own deadline from the budget when the call arrives (TRN-36), so the provider's can be later than the caller's; TRN-38 holds the caller to its own deadline, on its own clock."
- **Spec 03 (outline).** One action is `POST /<name>/v<N>/<action>`, with the call context in `Authorization`, `Neolith-Principal`, `Neolith-Timeout`, `Idempotency-Key`, `traceparent` and `tracestate`. The provider's host "authenticates the calling app before it reads the request body or any call-context header". A connector takes the kind from the body only; a non-success response without a neolith error body is `unavailable`; a success response that is not a valid reply is `internal`. An incoming `tracestate` is passed on.
- **[0008](0008-typed-contract-errors-in-both-modes.md) (Accepted).** Only hosts and transports produce `unavailable` and `timeout`, and "a transport failure surfaces only as one of those two". `timeout` leaves the outcome unknown.
- **[0017](0017-call-context-explicit-at-the-action-ambient-for-propagation.md) (Accepted).** The caller's order of checks (Decision 9) ends with the budget check (step 4) and the send (step 5). The connector retries only an idempotent action, only on `unavailable`, within the call's one deadline.
- **The other step 5 records.** [0014](0014-pluggable-connector-transports.md), as amended for remote providers, admits one transport option, `url`, an origin in one spelling, and assumes of this record (its A2) that the client "sends each call at most once, opens no connection when it is built, and bounds connection establishment so that a provider that cannot be reached fails with `unavailable` also on a call that has no deadline", leaving pooling, TLS trust and retry of an attempt that sent nothing to this record. [0011](0011-the-host-serves-contract-endpoints-itself.md), as amended for provider endpoints, fixes the replies: 200 with the reply's JSON text, 204 for an empty reply, an error with the status of its kind; it notes that "a neolith caller sends `Content-Length`", and it never refuses a `tracestate`. 0027 fixes the token, the principal header and what a host does with `tracestate`. None of them is Accepted; this record follows them as working assumptions.

### What the code and the libraries do

The connector at 0.1.0a2 is synchronous: `Connector._call` runs the caller's checks, builds a `Sent` (principal, trace, `tracestate`, `budget`, key, caller) and calls `Transport.call(action, request, context) -> bytes | None`, raising `Failure`; any other exception from a transport is logged and reaches the caller as `internal` (`_carry`). It then discards an outcome that came back after the caller's deadline (`src/neolith/_connector.py`). `Scope.budget` applies the floor and `BUDGET_CAP` (`src/neolith/_context.py`). Actions are synchronous (`_contracts.py` refuses a coroutine function). `neolith.testing` holds only `boot()` (0022 Decision 7); the test harness of 0008 Decision 2 has not landed.

Python was read at 3.13.5, and probed on 3.12.13 and 3.13.5. Paths are relative to `Lib/`.

1. `http.client.HTTPResponse` reads the status line and headers through `sock.makefile("rb")` (`http/client.py`, line 269), at most 100 fields (`_MAXHEADERS`, line 112) of at most 65536 bytes (`_MAXLINE`, line 111). `HTTPConnection.getresponse` builds it from `self.sock` (line 1426) and `send` writes with `self.sock.sendall` (lines 1053 to 1061). urllib3 builds on the same classes: its `HTTPConnection` subclasses `http.client.HTTPConnection` and reads every response with `super().getresponse()` (`urllib3/connection.py`, lines 113 and 638, 2.8.0). The parser is lenient where this transport needs it strict (`begin` and `_read_status`, lines 290 to 391, and probes): `begin` skips only `100`, so a `103` is returned as the final response with a body of length 0 and the connection still open, and the real response stays unread on the socket; the status is read with `int()`, so `+200`, `2_00` and `0200` are 200, and any `HTTP/1.x` is read as 1.1; `Content-Length` is read with `int()`, so `+10` and `1_0` are 10, and of two fields the first is used; a `Transfer-Encoding` other than exactly `chunked`, such as `gzip, chunked`, is ignored and `Content-Length` used; a `204` or `304` has no body whatever its framing fields say. In each case the connection counts as complete and reusable. A `BadStatusLine` carries the raw line, up to 65536 characters, CR and LF included. Three more readings are lenient. A chunk size is read with `int(line, 16)` (`_read_next_chunk_size`), so `0x5`, `+5`, `0_5` and ` 5 ` are each 5, and `-0` ends the body. Field lines go through `parse_headers` and `email.parser`, which splits one line on a bare CR, so `X-A: a\rContent-Length: 2` gives two fields, and which ends the header section at `Content-Length : 2` (a space before the colon), dropping it and every field after it. Persistence (`_check_close`) reads `Keep-Alive` and `Proxy-Connection` for HTTP/1.0 as well as `Connection`, and closes on any `Connection` value that contains `close`, such as `x-unclosed`. `putrequest` writes `Accept-Encoding: identity` straight after the request line unless `skip_accept_encoding` is given (line 1250). CPython's main branch is changing this surface: `getresponse` calls `begin(support_continue=...)`, and `_is_legal_content_length` and `_is_legal_chunk_size` are added.
2. A socket timeout bounds one operation. Since Python 3.5, `socket.sendall` and the `ssl` handshake, `read` and `write` treat it as "the maximum total duration" of that one call ([socket](https://docs.python.org/3.13/library/socket.html), [ssl](https://docs.python.org/3.13/library/ssl.html) docs). A timeout of `0` makes the socket non-blocking, and a negative one raises `ValueError`. `SSLSocket.sendall` loops over `send`, each with the full timeout (`ssl.py`, lines 1252 to 1264). `socket.getaddrinfo` takes no timeout at all; urllib3's own note says "Python's DNS resolver does not obey the timeout specified on the socket" (`urllib3/util/timeout.py`, line 91).
3. `ssl.create_default_context()` verifies the certificate and the host name, loads the system's trust store, and from 3.13 adds `VERIFY_X509_STRICT` and `VERIFY_X509_PARTIAL_CHAIN` (`ssl.py`, lines 706 to 713; the docs' "Changed in version 3.13" note), so 3.12 and 3.13 verify differently unless the flags are set. urllib3 2.8.0 follows each Python's default and sets the two flags only from 3.13 (`util/ssl_.py`, lines 292 to 296). Its `minimum_version` reads `MINIMUM_SUPPORTED`, while the docs say TLS 1.2 has been the minimum since 3.10. OpenSSL reads `SSL_CERT_FILE` and `SSL_CERT_DIR` for that store (`ssl.get_default_verify_paths()`, probe), and `OPENSSL_CONF` for its own configuration. `create_default_context` also reads `SSLKEYLOGFILE` and, when it is set, opens that file for append as the context is built, writes a header line to it, and then writes every session's secrets there (`ssl.py`, lines 723 to 727; probe on 3.12.13 and 3.13.5). `ssl.SSLContext(ssl.PROTOCOL_TLS_CLIENT)` followed by `load_default_certs()` never reads the variable, and gives the same `check_hostname`, `verify_mode`, `verify_flags`, options, ciphers and store as `create_default_context()` on both versions (probe).
4. `urllib.request.getproxies()` reads `*_proxy` variables and drops `HTTP_PROXY` when `REQUEST_METHOD` is set, because a CGI server may set it from a client's `Proxy:` header (`urllib/request.py`, lines 2518 to 2522). `urllib.request` sends `Connection: close` on every request (line 1304), so it never reuses a connection.

Django was read at 5.2.19 and 6.1.3; the cited code is the same in both.

The development server and `LiveServerTestCase`'s `ThreadedWSGIServer` keep a connection open while a response carries `Content-Length`, and close it otherwise; they have no idle timeout (`core/servers/basehttp.py`, `ServerHandler.cleanup_headers`, lines 133 to 155 in 6.1.3, and `WSGIRequestHandler.handle`).
6. asgiref's `sync_to_async` defaults to `thread_sensitive=True`, which runs the function on the current context's single-thread executor, and Django's `ASGIHandler` sets one such context per request (`asgiref/sync.py`, lines 477 and 507 to 515), so the blocking calls of one async request run one after another. Django's `async_unsafe` refuses ORM use from a thread that runs an event loop, unless `DJANGO_ALLOW_ASYNC_UNSAFE` is set (`utils/asyncio.py`).

Servers that a provider may run under close idle connections on their own clocks: gunicorn 27.0.1's `keepalive` defaults to 2 seconds for its keep-alive workers, and its default `sync` worker keeps no connection (`gunicorn/config.py`, class `Keepalive`, line 940); uvicorn 0.54.0's `timeout_keep_alive` defaults to 5 (`uvicorn/config.py`, line 234).

Other systems, for the parts this record has to write itself:

11. **Go's `net/http` and `net`.** The transport reads past every `1xx` other than `101` to the final response, bounding them by the total size of their header sections (earlier releases also counted at most 5), and reports them through `Got1xxResponse` (`src/net/http/transport.go`, `readResponse`). h11, which httpx uses, reports them as `InformationalResponse` and reads on. `net.Dialer` gives each resolved address `partialDeadline`: the time left divided by the addresses left, at least 2 seconds (`src/net/dial.go`). `net.Conn.SetDeadline` takes an absolute time that applies to every later read and write. Lookups of one name in flight are shared (`lookupGroup`, `src/net/lookup.go`); a caller that stops waiting forgets the lookup only when no other call joined it (`ForgetUnshared`). On a reused connection, a request whose write failed before any byte was written (`nothingWrittenError`) is tried again on a new connection, idempotent or not (`shouldRetryRequest`).
12. **gRPC and Envoy.** grpc-go writes `grpc-timeout` as `time.Until(deadline)` in `createHeaderFields`, called when a stream opens on a transport that is already connected (`internal/transport/http2_client.go`, lines 556 and 636). gRPC retries an RPC transparently when it "never left the client", whatever the retry policy ([gRFC A6](https://github.com/grpc/proposal/blob/master/A6-client-retries.md#transparent-retries)), and otherwise only under a declared policy bounded by the call's deadline and its `retryableStatusCodes`. Dapr declares timeouts, retries and circuit breakers as named policies applied to targets ([resiliency policies](https://docs.dapr.io/operations/resiliency/policies/)). aiohttp caches resolutions for 10 seconds by default (`ttl_dns_cache`).

The same exchange through `http.client.HTTPConnection` over a socket wrapper that sets the timeout to the time left before each `recv_into` and each `send` failed at 0.50 s, whether the drip was in the body or in the header lines. A server that sent `103`, waited 200 ms and sent `200 reply-one` had its `reply-one` read by the next request on the same `http.client` connection. `getaddrinfo("localhost")` took about 101 µs inline and about 345 µs run in a new thread and joined (2000 runs each, `timeit`).

### Forces

- **The deadline exactly** (TRN-4, TRN-27, TRN-38, spec 00). The caller stops waiting at its deadline in every phase, and the budget it sends is what remains when the request leaves, so the provider's deadline is later than the caller's only by the request's transit and any queueing before the provider's host reads it.
- **Sent at most once** (TRN-17), with retries left to the connector (TRN-8), so the rule is the same over every transport.
- **One form per input** (the step's design gate, K2): every byte the client writes is named by the admitted set, each response it accepts has one reading, and nothing in the environment changes where or how a call goes.
- **Every adopter installs a dependency** (K5, 0005 Proposed, principle 12). A dependency also brings a version range that an adopter's own use of the same library must intersect.
- **Secure by default** (K9): TLS verification on, no way to turn it off outside tests, no secret written outside the process.
- **Testable on one machine** (T3): no network beyond the local machine, and no sleeping to wait.

## Options

1. **httpx 0.28.1**, as the roadmap assumed. Sync and async under one API, a pool, and a mock transport. Its timeouts are per operation, its budget header is fixed before a connection is chosen, it brings six packages, and its next major version is a redesign still in pre-release.
2. **urllib3 2.8.0.** No dependencies, typed, maintained, sync only. Its parser is `http.client`; what it adds is a pool and retries, and the retries have to be turned off.
3. **requests 2.34.2.** Familiar, sync only, four dependencies, and it reads proxies, credentials and a CA bundle from the environment by default.
4. **aiohttp 3.14.5.** A true total timeout, async only, with compiled dependencies.
5. **`urllib.request`.** No dependency and no pool.
6. **The standard library's `ssl` and `socket`, with a request writer and a strict HTTP/1.1 response reader of the transport's own**, a small pool per provider origin, and a socket wrapper that bounds every blocking step by the call's deadline.

## Decision

Option 6. The admitted set comes first; Decisions 1 to 9 each weigh their alternatives.

### The admitted set

**Settings.** This record adds no key to `NEOLITH` and no option to a remote provider's entry; 0014's `OPTIONS` stays exactly `{"url": ...}`. Every value below is a constant of the transport.

**The environment.** neolith reads nothing for the client: no proxy variable (`HTTP_PROXY`, `HTTPS_PROXY`, `ALL_PROXY`, `NO_PROXY`, in any case), no `.netrc`, no CA-bundle variable of another library. The environment reaches a call only through the system's own configuration, each part as its owner defines it: the system resolver's (`/etc/hosts`, `resolv.conf` and the variables the C library reads for them), and OpenSSL's (`OPENSSL_CONF`, and `SSL_CERT_FILE` and `SSL_CERT_DIR` as part of the trust store; Context, point 3). Python's `SSLKEYLOGFILE` is never read: the transport builds its TLS context without `create_default_context()`, which opens that file (Decision 6), so no setting or variable makes the client create, open or write a file.

**The request the client writes**, in this order, and nothing else:

```
request-line       = "POST" SP "/" name "/v" N "/" action SP "HTTP/1.1"     ; from the contract and the action
Host               = host [":" port]          ; the url's authority exactly as written (0014's grammar)
Accept-Encoding    = "identity"               ; no content coding in a reply (RFC 9110, section 12.5.3)
Content-Type       = "application/json"
Content-Length     = 1*DIGIT                  ; the request's length; never chunked
Authorization      = "Bearer" SP token        ; on every call sent; three base64url parts (0027 Decision 9)
Neolith-Principal  = 1*b64char                ; the principal's sent form, base64url; only when the call has a principal (0017 Decision 1)
Neolith-Timeout    = %x31-39 0*9DIGIT         ; only when the call has a deadline; read as Decision 2 says
Idempotency-Key    = sf-string                ; 1 to 255 characters (0017 Decision 3)
traceparent        = W3C Trace Context        ; built from the trace and a new span, lowercase hex
tracestate         = W3C list                 ; only when the call's tracestate is not empty; at most 512 characters
body               = the request's JSON text, as the sender wrote it (0007)
```

No `User-Agent`, `Accept`, `Connection`, `Expect`, `Cookie`, `Proxy-*` or `Transfer-Encoding` field is sent. Every value above is bounded before it reaches the transport by the check named beside it, and none of those grammars admits CR, LF or any other control character, so no value can break a field line. The one value that is not built by the caller's host is `tracestate`, which is passed on from an incoming request; a host passes one on only as a W3C list, shortened by whole entries to at most 512 characters, and drops a value that is not such a list (0027 Decisions 6 and 11), so it too meets its grammar here. A call with no calling app, or from an app with no signing key, is refused before any of this, so every call written carries `Authorization` (0027 Decision 9). The transport checks each value against its grammar again before writing. A mismatch there is a bug in the caller's host, not a transport failure in 0008's sense, since nothing reached the network: like any exception a transport raises other than `Failure`, it is logged and reaches the caller as `internal` (`_carry`), as 0017 Decision 1 treats a principal that is not valid.

**The response the client accepts**, before spec 03's mapping. Anything outside the table fails the call with `unavailable`, and the connection is closed, never pooled.

| Part | Accepted |
|---|---|
| Status line | `( %s"HTTP/1.1" / %s"HTTP/1.0" ) SP %x31-35 2DIGIT SP *( HTAB / SP / VCHAR / obs-text ) CRLF`, as RFC 9112 sections 2.3 and 4 give it: the version is case-sensitive, the space after the status is always there, and the reason may be empty. At most 65536 bytes with its CRLF. The status is read from those three digits, not with `int()`. |
| Interim responses | every `1xx` other than `101`, `100` included, is read with its header section and discarded, at most 5 before the final response; each header section has the limits below. A sixth, or a `101`, is outside the table. |
| Header section | at most 100 fields, each line at most 65536 bytes. |
| Field lines | each is `field-name ":" OWS field-value OWS` ending in CRLF: `field-name` a token, no whitespace before the colon, no CR or LF inside the line, and no obs-fold (a line that starts with SP or HTAB). A trailer section after a chunked body is read under the same rules and limits, and discarded. |
| Chunk size | `chunk-size [ chunk-ext ] CRLF`, with `chunk-size = 1*16HEXDIG` and `chunk-ext = *( BWS ";" BWS token [ BWS "=" BWS ( token / quoted-string ) ] )`, as RFC 9112 section 7.1.1 gives it, with the size held to 16 hexadecimal digits, so no control character other than HTAB; at most 65536 bytes with its CRLF. Extensions are read and ignored. A size of zero (`1*"0"`) is the last chunk; every other chunk's data is followed by CRLF. |
| Persistence | from the options of every `Connection` field line, read as one list (RFC 9110 section 5.3), each compared as a whole token ignoring case, so `close` anywhere closes the connection: `close` closes the connection, and in an `HTTP/1.0` response only `keep-alive` keeps it. `Keep-Alive` and `Proxy-Connection` are not read. |
| Framing | at most one `Content-Length` field, whose value is `1*DIGIT` of at most 18 digits, so its conversion cannot fail (Python refuses `int()` of more than 4300 decimal digits); a longer value is outside the table; at most one `Transfer-Encoding` field, whose value is exactly `chunked` (any case), and only in an `HTTP/1.1` response; never both. With neither, the body runs to the end of the connection; over `https` that end is a TLS `close_notify`, and a close without one is outside the table (RFC 9112 section 9.8). The body is read in full; one that ends early, by a reset, a ragged TLS end or a close before its length, is outside the table. |
| `204`, `304` | no body, whatever the framing fields say (RFC 9112, section 6.3); when a `Content-Length` other than `0` or a `Transfer-Encoding` is present, the connection is closed after the response, never pooled. `204` is a reply; `304`, like every status that is not a reply, is handed on as a non-success status. |
| Every other header field | not read, apart from `Connection`; no content coding is undone, no redirect followed, no cookie kept. |
| `Connection: close`, `HTTP/1.0` without keep-alive, or a body to the end of the connection | the connection is closed after the body. |

The client hands the transport the final status and the body's bytes. The transport maps them as spec 03 and 0011 Decision 4 say: 200 with the reply for an action that has one, 204 for an action whose reply is empty, and the other pairing to `internal` (TRN-18); a neolith error body to its kind; anything else to `unavailable` or `internal`.

**Failures of the client, by phase.** "Before writing" covers name resolution, connecting, the TLS handshake and the budget check of Decision 2.

| Phase | The deadline passes | Any other failure |
|---|---|---|
| Before writing | `timeout`: `the deadline passed before the call was sent` | `unavailable`: `the provider at <origin> could not be reached: <reason>` |
| Writing | `timeout`: `the deadline passed before the call ended; the action might have run` | a response the provider already sent, read within the deadline, is mapped as usual; with none, `unavailable`: `the connection to the provider at <origin> failed before the response was complete` |
| Reading the response | `timeout`: as for writing | `unavailable`: as for writing |
| A response outside the table above | — | `unavailable`: `the provider at <origin> did not answer in HTTP/1.1` |

The two `timeout` messages are the connector's own texts today (`_NOT_SENT`, `_LATE`). The `<reason>` is the first of: `its name did not resolve`; `no connection within 10 seconds`; `no address accepted a connection`; `its TLS certificate did not verify (<OpenSSL's verify message>)`; `the TLS handshake failed`. `<origin>` is the url as configured. No message carries a header value, a token or a body. The transport logs each `unavailable` once on the `neolith` logger at `WARNING`, with the trace identifier, the contract, the action, the phase, the exception's class and the `repr` of its text cut to 200 characters, since that text can carry bytes the provider sent.

**No frame of the client reaches an error report.** While a request is written, the client's frames hold its header bytes, the token among them, as plain locals (the writer builds each request as one buffer before it sends it). The transport holds the token in 0027's wrapper object until it writes the header, and it reports every failure as a `Failure`. The connector builds the caller's error from that `Failure` and raises it outside any exception handler, as `_carry` arranges at 0.1.0a2, so the error carries neither the transport's exception as its cause or context nor the client's frames. Django's technical 500 page, which lists every frame's locals when `DEBUG` is true, therefore shows none of them for a caller's view; Django's `sensitive_variables` would not hide them there, since it applies only when `DEBUG` is false (0027, Context).

**Constants.**

```
connect cap        = 10 s     ; resolve + connect + TLS handshake, on every call that opens a connection
per address        = the time left in the phase / the addresses left, at least 2 s or the time left if less
interim responses  = at most 5 before the final response
idle connections   = at most 10 per provider origin, newest reused first
idle expiry        = 1 s
connections used   = no limit; a call never waits for a pool slot
TCP                = TCP_NODELAY; SO_KEEPALIVE with idle 60 s, interval 10 s, 6 probes where the socket module has those options
TLS                = ssl.SSLContext(PROTOCOL_TLS_CLIENT) with load_default_certs(), sockets wrapped with suppress_ragged_eofs=False, minimum TLS 1.2, VERIFY_X509_STRICT and VERIFY_X509_PARTIAL_CHAIN on every Python; SSLKEYLOGFILE never read
HTTP               = HTTP/1.1 only; no ALPN, no HTTP/2
log text           = repr, at most 200 characters
```

### 1. The client is the standard library, and the transport adds no runtime dependency

The HTTP transport writes each request's bytes itself, exactly as the admitted set gives them, and reads the response with a strict HTTP/1.1 reader of its own, through the deadline-bounded socket wrapper (Decisions 2 and 3). TLS is `ssl`; sockets are `socket`. The writer, the reader, the pool, the socket wrapper and the resolution of Decision 2 are code in the transport, private, and none of it calls or overrides a private name of the standard library. Their size is measured by a spike in the step 5 pull request rather than estimated here. K5 is met by adding nothing: `pyproject.toml` keeps `Django` and `pydantic` as its only runtime dependencies.

The precedent is Go, whose `net/http` reads every response with a parser of its own over the standard library's connections (Context, point 11), and h11, a parser of the same rules with no I/O. `ssl` and `socket` are maintained and security-fixed with the interpreter adopters already update.

Alternatives weighed:

- **`http.client`, with its lenient readings overridden**, as urllib3 builds on it. Its connection class and request writer come with Python. Its response side is lenient in more places than the status line and `Content-Length`: chunk sizes, field lines and persistence too (Context, point 1). Making each strict means overriding or replacing `begin`, `_read_status`, `parse_headers`, `_read_next_chunk_size` and `_check_close`, private names that CPython's main branch is changing now, on every supported Python. A reader of its own is about the same amount of code, written against RFC 9112's grammar, which does not move.
- **httpx 0.28.1.** It is well designed and widely used, and its `AsyncClient` and `MockTransport` are real advantages. Three of this step's needs run against it. Its timeouts bound each socket operation, so a provider that drips its reply holds the caller past its deadline (probe: 1.65 s for 0.5 s), and name resolution is unbounded; meeting TRN-38 in sync code means replacing its network backend. Its headers are fixed before a connection is chosen, so `Neolith-Timeout` would count connection time twice, once on each side (Decision 2). Its defaults add four request headers, read proxy variables and trust certifi's bundle, each of which would be turned off. The cost to adopters is six packages, and a range of `httpx>=0.28,<1` while the 1.0 line is a redesign with a different API: an adopter who moves to httpx 1.x for its own code could not install neolith until neolith had been ported. None of these is a fault in httpx; they are what a general client chooses and this transport would undo.
- **urllib3 2.8.0.** The strongest alternative: no dependencies, typed, maintained, and a tested pool. Its parser is `http.client`, lenient in the same places (Context, point 1), so the strict reader of Decision 3 would be needed beneath it too. Its retries default to three and would be turned off on every call (Decision 5), and its total timeout has the same per-operation limit (Context, point 8), so the deadline would still need a wrapper under its connection. The pool is what would remain, at the cost of a range every adopter shares. requests and botocore each declare a urllib3 range of their own (`<3,>=1.26` and `!=2.2.0,<3,>=1.25.4`), so an adopter's resolver would carry one more constraint on the same package.
- **requests 2.34.2.** Familiar to every Django team. It brings four packages, urllib3's timeouts, and three environment inputs that would each be a second way to change a call (Context, point 9).
- **aiohttp 3.14.5.** Its total timeout is exact. It is async only: every synchronous call would need an event loop, in a thread the host would own. It brings seven packages, some compiled.
- **`urllib.request`.** No dependency, but it opens a connection per call (Context, point 4), raises for every non-2xx status, and reads proxy variables.

Principle 13 (*integrate over own*) asks the project to use what exists. Here what exists is the standard library's sockets and TLS; what neolith adds is a writer, a strict reader, a pool and a deadline, which no candidate offers for synchronous code in the form spec 02 needs. 0011 weighs django-ninja the same way.

The cost: neolith maintains a request writer, a strict response reader, a small pool and a socket wrapper, with their tests, instead of inheriting a library's. It depends on no private name of the standard library.

### 2. One deadline bounds every blocking step, and the budget is read when the request is about to be written

The call carries its deadline in one form. The private `Sent` holds the deadline on the caller's clock (`time.monotonic()`) in place of `budget`, and one private helper turns a deadline into a budget at a given moment: the time left in whole milliseconds rounded down, capped at 9999999999, or `None` with no deadline. The connector calls it at step 4 of 0017 Decision 9, as today; the in-process transport calls it when it dispatches; the HTTP transport calls it once a connection is ready. So the floor of TRN-28 and the cap of TRN-29 are written once. Every blocking step is bounded by the time left at the moment it starts:

- **Name resolution** runs `socket.getaddrinfo` in a new daemon thread, and the caller waits for it at most until the earlier of its deadline and the connect cap. Calls to one origin share the resolution in flight, as Go's `lookupGroup` shares one lookup (Context, point 11), and each waits on it for its own limit. When every call waiting on a resolution stops waiting before it ends, the pool forgets it: the next call starts its own, and the forgotten thread runs to its end with its result unused. Go's `ForgetUnshared` forgets a lookup only when no other call joined it, so in Go a stuck lookup that two calls shared still holds later calls until it returns; the pool does not. The result is not cached. A host that is an IP address is not resolved. Measured cost: about 0.25 ms more than resolving inline, only when a connection is opened.
- **Connecting** tries each address `getaddrinfo` returned, in its order, one after another. Each gets Go's `partialDeadline`: the time left in the phase divided by the addresses left, at least 2 seconds, or all the time left when that is less (Context, point 11). An address that drops packets silently then costs its share, not the whole phase.
- **The TLS handshake** gets the time left in the phase as its socket timeout, which `ssl` treats as a total for the handshake (Context, point 2).
- **The connect cap**, 10 seconds, bounds the three steps together, on every call that opens a connection, deadline or not (0014's A2). When the cap ends the phase, the call fails with `unavailable`; when the deadline does, with `timeout`.
- **The budget** is read once a connection is ready, through the helper. Under 1 ms, the call fails with `timeout`, unsent, and the connection goes back to the pool.
- **Writing and reading** go through a wrapper that sets the socket's timeout to the time left before each `send` and each `recv_into`, as `SetDeadline` gives every Go read and write one absolute time. The reader reads only through the wrapper, so a header line or a body that arrives slowly is cut at the deadline.
- **No time left.** Before every connect, handshake, `send` and `recv_into`, a time left of zero or less fails the call with `timeout` without calling the socket, so a deadline that passes at a boundary never reaches `settimeout(0)` or a negative timeout (Context, point 2).
- **At the deadline** the connection is closed, never pooled, and the call fails with `timeout`. The connector's check on the outcome stays as it is.
- **With no deadline**, writes and reads have no timeout. `SO_KEEPALIVE` with the constants above detects a peer whose host or network has gone; a provider that holds an open connection without answering holds a call with no deadline indefinitely, as TRN-27 allows. A call with neither has no deadline, and this record adds none.

So the caller stops waiting at its deadline in every phase, and the provider's deadline is later than the caller's only by the request's transit and any queueing before the provider's host reads it, as the relative budget of spec 03 intends. grpc-go computes `grpc-timeout` the same way, on a transport that is already connected (Context, point 12).

Alternatives weighed:

- **A timeout per phase, set once from the deadline**, as httpx and urllib3 do. Simple. A provider that sends a byte before each timeout holds the caller as long as it likes (Context, points 7 and 8), and resolution is not bounded.
- **The budget read when the connector hands over the call**, as today's `Sent.budget`. No change to `Sent`. The time spent resolving and connecting, up to the cap, would then be counted again by the provider, so its deadline could end up to 10 seconds later than the caller's.
- **`Sent` carrying both the budget and the deadline.** No change for the in-process transport. One input in two forms, which can disagree, and the floor and cap written twice.
- **The configured timeout instead of the time left**, as Envoy's `x-envoy-expected-rq-timeout-ms` carries (Context, point 12). It needs no reading at send time. TRN-27 defines the budget as what remains, so a nested call would carry more than its parent has.
- **A watchdog thread that shuts the socket down at the deadline.** One timer for all calls. It is process-wide state with its own lifecycle (K6), and it races with a connection being returned to the pool.
- **Running each exchange in a worker thread and waiting on its future.** Exact for the caller, and it covers resolution too. Each call then crosses threads, and the worker keeps running after the caller has gone, holding the connection.
- **Resolving inline.** No thread. The caller waits as long as the system resolver does, which its configuration, not the deadline, decides.
- **A short-lived resolution cache**, as aiohttp keeps for 10 seconds (Context, point 12). It saves a thread per new connection for a caller that calls rarely. It is a second cache above the system resolver's own, which already caches where it is configured to (nscd, systemd-resolved), and it would keep using an address for up to its lifetime after DNS has moved the provider.
- **Every address at once, or Happy Eyeballs** (RFC 8305, asyncio's `happy_eyeballs_delay`, aiohappyeyeballs). The fastest connection wins, and a broken IPv6 path costs about 250 ms. It needs a thread or a selector loop per connect and opens sockets that are then thrown away. The partial deadline bounds the same failure without either; racing is left for a measured need.

### 3. The client writes exactly the admitted request, and reads only status, framing and body, strictly

The transport writes the request line and every field itself, in the order of the admitted set, with its own `Host` from the url as written. `Content-Length` is always sent, since a WSGI server reads a chunked body without it as empty, and 0011 requires it (its row 11). `Accept-Encoding: identity` is sent because RFC 9110 lets a server choose any coding when the field is absent.

On the response side the reader reads the status, the field lines, the framing, the body and persistence, and nothing else, and it reads each in one way: each status line against the admitted grammar, past interim responses; each field line against `field-name ":" OWS field-value OWS`; the framing fields before the body; each chunk size as `1*HEXDIG`; and persistence from the `Connection` options alone. Every spelling `http.client` reads beyond these (Context, point 1) is outside the table. RFC 9110 section 15.2 asks that "a client MUST be able to parse one or more 1xx responses received prior to a final response, even if the client does not expect one", and RFC 9112 section 6.3 says a response with both `Transfer-Encoding` and `Content-Length` "ought to be handled as an error", and that a client which receives an invalid `Content-Length` "MUST close the connection". A provider (or a proxy before it) that sends `103` and then `200` has run the action, so reading on to the final response is what the call's outcome needs; a connection on which any framing is ambiguous is closed, because what is left on it may be the start of the next call's reply. `101` is outside the table, since the client asks for no upgrade.

It never follows a redirect: a provider url that redirects is a misconfiguration, which reaches the caller as `unavailable` (spec 03, a non-success response without a neolith error body). It never decodes a content coding; a reply a proxy compressed is not valid JSON, so it is `internal`, or `unavailable` for an error.

The body the client hands on is read as 0007 Decision 3 asks of a network receiver: the connector runs CON-42's text rules, the description check and CON-40 on a reply or a neolith error body that arrived over HTTP, then the declared type's validator on the same text, through the same receive switch that 0011 Decision 3 turns on for requests. The detail of an error whose kind the caller does not know (CON-28) is read only after the body has passed CON-42.

Alternatives weighed:

- **`http.client`'s own reading**, as urllib3 inherits it. Nothing to write. A `103` becomes a non-success status, so an action that ran reaches the caller as `unavailable` (and, under step 6, an idempotent one would be sent again), and the final response is left for the next call on that connection.
- **Never pool after any `1xx`, and hand the `1xx` on.** Smaller. A provider that sent `103` and then `200` has run the action, and the caller would still see `unavailable`.
- **Accept repeated identical `Content-Length` values**, which RFC 9112 section 6.3 lets a recipient do. More forgiving. A second form for one length, and no neolith provider sends one.
- **Check `Content-Type` on replies.** It would catch a proxy's HTML page earlier. Spec 03 defines a reply and a neolith error body by their content, and the connector checks that content against the contract (TRN-12, TRN-18), which a media type cannot. A check here would add an outcome the specification does not have.
- **Send `User-Agent: neolith/<version>`.** Useful in a provider's logs. It discloses the version to every intermediary and is one more field with no rule in spec 03; the calling app is already named by the token.
- **Follow redirects for idempotent actions.** A redirect resends the request, which TRN-17 forbids under `single`.

### 4. One pool per provider origin, owned by the set-up, and a call never waits for a slot

Transports whose `url` is the same origin share one pool, built at set-up with the transport and holding no connection until the first call (0014's A2). The pool keeps at most 10 idle connections, reuses the newest first, and drops one idle for more than 1 second. Before reusing a connection it checks, without blocking, that the socket is not readable, by `poll` where the platform has it and `select` otherwise, as urllib3's `wait_for_read` chooses; a readable idle socket has been closed or sent something unasked, and is dropped. A connection is returned only after a final response inside the admitted table, read in full, that does not close it, and only when no byte past the response has been received: the reader's buffer is empty and, for `https`, `SSLSocket.pending()` is 0, since TLS decrypts a whole record at once and keeps what follows the response where `poll` cannot see it. RFC 9112 section 6.3 says a client "MUST NOT process, cache, or forward such extra data as a separate response". A connection is never returned after a write failed, a deadline passed, a `204` or `304` carried framing fields, or a response was outside the table. `REMOTE_PROVIDERS` cannot change after set-up (0014 Decision 6). The private `over_http` test seam of 0014 brings a pool for its origin when it is entered, unless the set-up already holds one, and closes a pool it brought when it exits: its idle connections at once, and each one in use when its call ends.

**Fork.** A forked child holds none of the parent's state for the client. The transport registers `os.register_at_fork(after_in_child=...)`, which empties every pool, gives every pool and every in-flight resolution record a new lock, and forgets every resolution in flight, since its thread does not exist in the child; a child that waits on a lock held by a parent's resolution thread would otherwise wait forever. A pool also records the process id that built it and starts empty in another process, for a child made without `os.fork`.

There is no limit on connections in use. Each calling thread holds at most one connection per call, so the host's own threads bound them.

The 1 second expiry is below the idle limits of the servers a provider commonly runs under with keep-alive (gunicorn's 2 s for its keep-alive workers, uvicorn's 5 s; Context), so the client drops a connection before the server does, rather than writing a request into one the server is closing. Under gunicorn's default `sync` worker, which keeps no connection, the race does not arise and the pool holds nothing. A request written into a connection that the server closes anyway fails with `unavailable` and is not resent (Decision 5), unless nothing of it was accepted.

Alternatives weighed:

- **No pool**, a new connection per call, as `urllib.request` does. Nothing to expire or check. Each call then pays a TCP and, for `https`, a TLS handshake.
- **httpx's limits**: 100 connections, 20 idle, 5 s expiry. A 5 s expiry outlives gunicorn's default for keep-alive workers, which is the race the shorter expiry avoids, and a cap on connections makes a call wait for a slot, a queue inside the caller that its deadline pays for and the provider cannot see.
- **One pool per contract entry.** Simpler bookkeeping. Two contracts at one host would hold separate connections to the same origin.
- **A pool per thread.** No lock. A thread pool's idle connections would then multiply with the threads.

### 5. The client never sends a call twice, and retries belong to the connector

The client has no retry: it never resends a request, never reconnects after any byte of a request has been accepted by the socket, and never follows a redirect. Trying each resolved address once, within one connect phase, is one attempt. A pooled connection dropped by the check of Decision 4 is replaced before anything is written, which is not a resend. The same race caught a moment later is not a resend either: when the first `send` on a reused connection fails before the socket has accepted any byte of the request, the transport closes it and opens one new connection, within the same deadline and connect cap, once. The request is built again on the new connection, with the budget read once that connection is ready (Decision 2); under 1 ms, the call fails with `timeout`, unsent. The provider cannot have seen a request of which no byte left the client. This is gRPC's transparent retry of an RPC that "never left the client", Envoy's `reset-before-request` and Go's `nothingWrittenError` (Context, points 11 and 12), and, as in Go, it applies only to a reused connection. An attempt to connect that fails is not repeated: the call fails with `unavailable`.

When step 6 brings TRN-8, the retry is the connector's, decided by the action's `idempotent` flag, on `unavailable`, within the one deadline, the same over every transport. This is where Envoy (`retry_on`, each try's `per_try_timeout` inside the route's timeout), gRPC (a declared policy bounded by the deadline) and Dapr (named resiliency policies) also put it: declared above the client, bounded by one deadline (Context, point 12). This record fixes only that the client underneath never adds a retry of its own. Whether a try gets a timeout of its own inside the deadline, as gRPC's and Envoy's do, is step 6's question.

Alternatives weighed:

- **Retry a connection attempt that sent nothing**, as httpcore's `retries` and urllib3's `Retry` can. Nothing reaches the provider, so it is safe. It hides a provider that is starting or failing behind a delay, and spends the deadline on a policy that TRN-8 gives to the connector (principle 6). The replacement above differs: it follows a failure of a connection the pool chose, not of the provider, and happens once.
- **No replacement after a first `send` fails.** Simplest. A non-idempotent call would fail with `unavailable` on a race the provider never saw.
- **Resend on a stale pooled connection when no response byte arrived**, as Go's `net/http` does for requests it considers idempotent, a set that includes any request with an `Idempotency-Key` field. Every neolith call carries that field, so the rule would resend non-idempotent actions after bytes may have reached the provider, which TRN-17 forbids.

### 6. TLS verifies against the system trust store, the same way on every supported Python, and cannot be turned off

One `ssl.SSLContext` per set-up, built when the first `https` provider's transport is built: `ssl.SSLContext(ssl.PROTOCOL_TLS_CLIENT)` with `load_default_certs()`, `minimum_version` set to TLS 1.2, and `VERIFY_X509_STRICT | VERIFY_X509_PARTIAL_CHAIN` set in `verify_flags`, so that Python 3.12 verifies as 3.13 does. Sockets are wrapped with `suppress_ragged_eofs=False`, so a TCP close with no `close_notify` raises instead of reading as the body's end (the response table, Framing). This is what `create_default_context()` gives on both versions, without reading `SSLKEYLOGFILE`, which `create_default_context()` opens and writes to as the context is built (Context, point 3). The url's host is the name checked; a name is also sent as SNI, and an IP address is not sent and is checked against the certificate's IP entries. No client certificate is sent: a backend on mutual TLS is a later record (spec 03). Nothing turns verification off (K9).

A provider behind a private certificate authority is trusted the way the system trusts it: the authority in the system store, or `SSL_CERT_FILE` or `SSL_CERT_DIR` for this process, which OpenSSL reads. This answers 0014's open question 1 for 0.1 without an option. Strict verification asks that authority to follow RFC 5280: the authority's certificate carries `basicConstraints` marked critical, a `keyUsage` with `keyCertSign` and a subject key identifier, and every certificate it issues carries an authority key identifier. An authority without them fails on every supported Python, with OpenSSL's message in the `unavailable` reason; the guide names these extensions.

**The test seam.** The context is built by one private function of the transport. The TLS tests replace that function, inside the test process, with one that builds the same context and then trusts the test authority (trustme's `configure_trust`); no setting, option or variable can reach it, so production trust has the one form above (K9).

Alternatives weighed:

- **Each Python's own default**, as urllib3 does (Context, point 3). A private authority that is not RFC 5280-conformant keeps working on 3.12. A deployment then verifies differently on two supported Pythons, and the failure appears on the day it moves to 3.13, rather than when the provider is first configured.
- **certifi's bundle**, as httpx and requests use. The same roots on every machine. A private authority then needs a second mechanism beside the system's, and certifi becomes a dependency (MPL-2.0).
- **truststore**, which asks the platform's verifier. It helps most on macOS and Windows, where OpenSSL's default paths may be empty. It is a dependency, and a Linux deployment gains nothing over OpenSSL's store.
- **A `ca_file` option in the entry.** Explicit per provider. A second way to say what the system store says, and a path that differs per environment inside the `NEOLITH` setting.
- **Admit `SSLKEYLOGFILE`** as OpenSSL's debugging input, with a `check --deploy` warning. Useful for reading captured traffic while debugging. A variable inherited by a process would write every bearer token and principal header in readable form to a file; the provider's own logs, and a test against a local server, serve debugging without it.

### 7. Proxies are not supported in 0.1, and no environment variable redirects a call

The client connects to the provider's origin directly. It does not read proxy variables (admitted set), so an inherited `HTTPS_PROXY` cannot send a call, and its bearer token, through a host the deployer did not name for it. Calls between apps usually stay inside one network, where proxy variables often exist for outbound traffic and `NO_PROXY` has to list each internal name.

Alternatives weighed:

- **Honour the variables**, as httpx and requests do by default. Familiar. A setting outside `NEOLITH` would then change where calls go, a second form of the provider's address, and the spellings vary between tools (`NO_PROXY` matching, case, CGI's `HTTP_PROXY`; Context, point 4).
- **A `proxy` option in the entry, now.** The transport would write `CONNECT` itself, as it writes every request. No deployment in step 5 needs it, and adding a key later is compatible.

### 8. In 0.1 the client is synchronous, and a call from async code is made as an in-process call is today

The HTTP transport is synchronous, as the connector, the in-process transport and actions are. This record changes nothing in how a connector call made from async code behaves: a synchronous call made in a thread whose event loop is running blocks that loop until the call ends, in-process today and over HTTP alike, and 0017 Decision 9's order of checks is unchanged. The guide for the HTTP transport says so, and says that async code calls a connector through `asgiref.sync.sync_to_async`, whose default `thread_sensitive=True` runs the calls of one request one after another, each up to its deadline, so an `asyncio.gather` over remote calls does not run them in parallel (Context, point 6). Whether to advise `thread_sensitive=False` for remote fan-out, which moves an in-process action and a first principal resolution onto a worker thread with its own database connection, is open question 4.

An async connector, with an async HTTP transport, waits for async actions and their own record, together with the asynchronous first call that 0023 Decision 5 already describes. That record keeps the admitted set, the deadline rule, the pool rules (per event loop) and Decisions 5 to 7. This record's reader works on blocking sockets, so that record will need a reader for asyncio streams: h11 0.16.0 (MIT, no dependencies, typed) and httpx 1.x, once released, are what it will weigh, with the facts of that time.

Alternatives weighed:

- **Refuse a connector call from a running event loop with `UsageError`, in every mode**, as Django's `async_unsafe` does for the ORM. It turns slow requests across a process into a visible failure (principle 6). It is wider than the client: it adds a check before step 1 of 0017 Decision 9, so a call whose principal fails to resolve would get `UsageError` instead of `internal`, it changes in-process behaviour released in 0.1.0a2, and it bears on the asynchronous first call of 0023. Under D2 it needs a record of its own that quotes the sentences it narrows and adds a spec 02 requirement (open question 5); the hazard it addresses exists today in-process, so the HTTP transport does not depend on it.
- **Run each call made from a loop in a thread on its own.** Transparent to the caller. It is concurrency the caller did not ask for, and in-process it would run an action outside the caller's thread, which TRN-6 forbids.
- **Adopt httpx now, for its `AsyncClient`.** Nothing in 0.1 is async, so the dependency would serve no caller, and it would fix the async design to the 0.28 line before 1.0 is settled.

### 9. The client is tested without a network, and the contract suite runs over a live server

- **The client's own tests** pass the transport one end of a `socket.socketpair()` through a private opener, and play the provider on the other end: a slow drip in the header and in the body; a reset before and after the request is written; an early `401` and a close while a large body is still being written; `Connection: close`; `HTTP/1.0`; `100` and `103` before a final `200`, including a `103` whose final response arrives after a pause, followed by a second call on the same connection; six interim responses; a `101`; each malformed status line (`+200`, `2_00`, `0200`, `HTTP/1.7`, `HTTP/2`); `Content-Length` as `+10` and `1_0`; two `Content-Length` fields; `Content-Length` with `Transfer-Encoding`; `Transfer-Encoding: gzip, chunked`; `Transfer-Encoding` in an `HTTP/1.0` response; a `204` with `Content-Length: 5`; too many headers; a chunked body cut short; a stale pooled connection, and a first `send` that fails on a reused one, whose replacement carries a budget read on the new connection; chunk sizes `0x5`, `+5`, `0_5`, ` 5 ` and `-0`; a field line with a bare CR, one with a space before its colon, and an obs-fold; `Keep-Alive` in an `HTTP/1.0` response, and `Connection: x-unclosed`; a deadline that passes in each phase, and one that passes exactly at a boundary; a status line of 65536 bytes, for the log's limit; `HTTP/1.1 200 ` with an empty reason (admitted), `HTTP/1.1 200` with no space and `http/1.1 200 OK` (refused); a `Content-Length` of 19 digits and one of 4301; a chunk size of 17 hexadecimal digits, and extensions `5\t;a` and `5;a="b\tc"` (admitted); a chunk extension with a bare CR, and a chunk-size line over the limit; `Connection: keep-alive` then `Connection: close`; over TLS, a `200` followed in the same write by a second response, then a second call that must not read it; and over TLS, a body without framing whose connection closes without `close_notify`; and a failure while the request is written, under a view with `DEBUG = True`, whose technical 500 page (`get_traceback_html()`) holds no token. The test's side waits on a `threading.Event`, never on `sleep` (T3), and deadlines are short.
- **Resolution and connecting** are tested against `127.0.0.1`, `[::1]` and `localhost` only, with a refused port and a listening socket that never accepts; the partial deadline is tested with a resolver stand-in that returns two addresses.
- **Fork** is tested by forking while a resolution is in flight, and checking that the child's first call resolves on its own.
- **TLS** is tested against a local server with a certificate from a test authority made at run time by trustme 1.2.1 (MIT or Apache-2.0; depends on cryptography and idna), a test-only dependency (K5's one-line reason), so no key is committed (K9), through the seam of Decision 6. The tests cover a valid chain, an untrusted one, a wrong host name, an IP address, an authority whose issued certificate lacks an authority key identifier (refused on every Python), and `SSLKEYLOGFILE` set in the test's environment (no file written).
- **The contract suite** runs against a `LiveServerTestCase` on `localhost`, reached through 0014's private `over_http` seam (its Decision 6). That server keeps connections alive (Context, point 5), so pooling is exercised there too.

Adopters will test their callers through the test harness of 0008 Decision 2, when it lands, which acts as a transport and can produce `unavailable` and `timeout`, so they need no HTTP mocking.

Alternatives weighed:

- **httpx's `MockTransport`** or a mocking library such as respx. Requests and responses as objects, with no sockets. It tests the code above the socket, which is not where the deadline and the pool live.
- **Recorded exchanges.** Repeatable, but they cannot show timing, and they go stale as the forms change.

Follows principles 5 (*same semantics over same mechanics*), 6 (*visible failure over transparent calls*), 8 (*one test suite over many code paths*), 10 (*Django-native over framework-new*) and 12 (*small core over broad features*), and K5, K6 and K9.

## Consequences

- No new runtime dependency. The roadmap's step 5 row reads "connector over the standard library's sockets and TLS" and its note on httpx is removed once this record is Accepted, in the pull request that closes step 5.
- neolith maintains a request writer, a strict response reader, a pool, a socket wrapper and threaded resolution, with tests that play the provider byte by byte. A bug there is neolith's to fix, not a library's. None of it relies on a private name of the standard library.
- The caller stops waiting at its deadline in every phase, and `Neolith-Timeout` carries what remains when the request leaves. The private `Sent` carries the deadline in place of the budget, and one helper turns it into a budget for the connector and for each transport.
- A call with no deadline to a provider that is alive but never answers waits indefinitely: keepalive finds only a host or path that has gone. Commands and background roots have no deadline unless given a timeout (TRN-48), so the guide advises that background work which calls a remote provider opens its root with a timeout, and that deployers keep a request deadline set.
- An unreachable provider fails within 10 seconds with `unavailable`, also on a call with no deadline, which leaves a call with the default 30 s deadline time for a retry in step 6.
- An address that silently drops packets costs its share of the connect phase, at least 2 seconds, before the next is tried. Happy Eyeballs is not attempted.
- Pooling helps bursts. A caller that calls one provider less than once a second pays a resolution in a thread, a TCP handshake and, for `https`, a TLS handshake on nearly every call; above 10 concurrent calls, the connections beyond 10 are closed after each use. The step 5 pull request measures that cost per call on the reference machine before the guide states it (K10).
- A provider or proxy that sends `103 Early Hints` is read through. A response with ambiguous framing fails with `unavailable` and its connection is closed, including some a lenient client would accept.
- A provider that refuses a call early (`401`, `403`) while a large body is still being written is reported as its kind when its response can still be read; a reset can discard that response first, and the call then fails with `unavailable`.
- A non-idempotent call can still fail with `unavailable` when a pooled connection closes after its bytes were accepted, even if the provider never processed it; only a first `send` that the socket refused is replaced.
- A deployer behind a mandatory outbound proxy cannot reach a remote provider in 0.1. A provider behind a private authority needs it in the system store or `SSL_CERT_FILE`, and the authority has to follow RFC 5280's extensions on every supported Python, Python 3.12 included. On macOS with a python.org build the system store may be empty until its certificate installer is run; the guide has to say so. `SSLKEYLOGFILE` has no effect on neolith's calls. Over `https`, a response with neither `Content-Length` nor chunked framing needs the provider's TLS `close_notify` to end; Python's own `SSLSocket.close()` sends none (only `unwrap()` does), so a provider behind such a server fails those responses with `unavailable`, and the guide says so. A response the server frames, as servers frame a body of known length, is not affected.
- The logs carry one `WARNING` per `unavailable`, with the failure's text cut to 200 characters. During an outage that is one line per call; a deployer who wants fewer adds a filter in Django's `LOGGING`.
- Async code calls a connector as it does today; the guide describes `sync_to_async` and its serialisation. Nothing in 0.1.0a2's in-process behaviour changes.
- Calls stay HTTP/1.1, one request per connection at a time; a busy caller holds as many connections as it has calls in flight.
- The specification gains, in the step 5 pull request, with IDs assigned there (P5) and in its own words (P2). In spec 02: a caller over a network stops waiting at its deadline in every phase of a call, name resolution included; a transport MUST NOT send a call again on its own, and a first write on a reused connection that the network refused before any byte left is not a send. In spec 03: the budget is read when the request is written, after a connection is ready; a caller sends `Content-Length` and `Accept-Encoding: identity`, follows no redirect and decodes no content coding; a caller reads past interim `1xx` responses to the final one and fails with `unavailable` a response whose status line, field lines, framing or chunk sizes are ambiguous; a caller sends a `tracestate` of at most 512 characters, which 0027 Decisions 6 and 11 make true of every value a host passes on.
- Tests, as Decision 9 lists, with one per row of the response and failure tables and each constant of the admitted set.

## Open questions

1. **A limit on the size of a reply or an error body.** The client reads a body in full, as the in-process transport hands on a reply of any size. The same holds for a neolith error body, whose detail the connector reads untyped for a kind it does not know (CON-28); a bound on that body before it is parsed was asked for when step 2 was reviewed (#12). A provider's host has `DATA_UPLOAD_MAX_MEMORY_SIZE` for requests; whether a caller needs a matching limit for replies, and with which kind, is for a later record with a measured need.
2. **An outbound proxy**, as an option of the entry (Decision 7), when a deployment needs one.
3. **The async transport's parser** (Decision 8), with async actions.
4. **`thread_sensitive=False` for remote fan-out** (Decision 8): whether the guide advises it, given that it moves an in-process action and a first principal resolution onto a worker thread, or whether async callers wait for the async connector.
5. **Refusing a connector call from a running event loop**, as a record of its own under D2 (Decision 8's first alternative), which would quote 0017 Decision 9 and 0023, add a spec 02 requirement, and say whether Django's `DJANGO_ALLOW_ASYNC_UNSAFE` is a second form of admitting the call or not read at all.
6. **An early refusal and a reset.** Whether the provider's host reads or drains the rest of a request body after refusing it early, as servers' lingering close does, so that the caller can read the refusal (the failure table's writing row; 0011 open question 8).
