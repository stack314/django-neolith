# Django host notes: request roots

These notes are django-neolith's implementation documentation, not part of any decision. They record how the host meets the request-root rules of [ADR 0017](adr/0017-call-context-explicit-at-the-action-ambient-for-propagation.md) Decision 4 on Django 5.2, and the edge cases found in review. The conformance cases at the end are in the test plan of roadmap step 4 (#11). Where these notes and ADR 0017 differ, the record governs.

**Middleware.** The host ships two middleware classes. Both are sync- and async-capable, and Django runs each in the mode of the handler inside it: under ASGI that is async, unless a sync-only middleware follows in `MIDDLEWARE`, in which case Django runs them in sync mode behind `sync_to_async` (`core/handlers/base.py`, `load_middleware`). They behave the same in both modes. A class that is missing or out of order stops the host at startup (K2); [ADR 0022](adr/0022-the-app-host-builds-settings-and-checks-before-it-serves.md) puts that check at set-up and in each class's constructor.
- **The root middleware** is placed outermost, and listed once: its constructor also resolves the other entries, which Django has already imported, and refuses the class under a second path. It opens the root when the request starts and keeps a reference to it; a request that arrives while the host is not set up is refused. Closing always goes through that reference, because on ASGI the middleware runs inside a task with its own copy of the context, so nothing outside it could find the root through the variable.
- **The principal middleware** is listed once in every host, after the root middleware, with or without principal backends ([ADR 0023](adr/0023-a-request-principal-comes-from-ordered-backends.md) Decision 6); with none it does nothing per request. With the Django-user backend it follows `SessionMiddleware` and `AuthenticationMiddleware`, which that backend checks when set-up builds it; its response phase therefore runs before `SessionMiddleware`'s, and the streamed-body case below relies on that. With any backend, Django's `UpdateCacheMiddleware` comes before it, which set-up (`neolith.E020`) and its constructor check, so the cache keys a response on the `Vary` it writes. `cache_page` is the one cache the host cannot check or reach: it stores a response at the view, before any middleware's response phase adds to `Vary` (ADR 0023 Decision 6). A view under `cache_page` that makes a contract call therefore adds the backends' declared request inputs itself, with `vary_on_headers` inside `cache_page` (`cache_page(60)(vary_on_headers("Authorization", "Cookie")(view))` for the Django-user backend), or is not cached; otherwise one user's page is served to another.

**Which app.** The app is found from the `view_func` that `process_view` receives, using `apps.get_containing_app_config`, for each request, so an app found once cannot outlive an override of the installed apps. The view and the objects it carries are read with `vars()` and `type()`, so no attribute hook of their author runs.
- **Class-based views.** A function `View.as_view` made carries `view_class` and, since its own code is Django's, is that class's code, judged by the class's own module. `as_view` also copies `dispatch`'s attributes onto it, so a `dispatch` decorated with `method_decorator(..., name="dispatch")` leaves a `__wrapped__` that leads to the inherited `View.dispatch`; `view_class` wins over it. No other Django function's `view_class` is honoured: one that `login_required` or `never_cache` copied from the view it wraps describes that view, so the wrapper follows its `__wrapped__` instead.
- **A wrapper's own code.** `functools.wraps` copies the wrapped view's `__module__`, `__dict__` and `view_class` onto the wrapper, so those describe the view, not the wrapper. A function's own module is the one whose globals it runs in, which `wraps` never changes. A copied attribute is trusted only on the function that set it: `__module__` never is, `view_class` only on the function `View.as_view` builds, and `model_admin` never on an app's wrapper, only on the function Django's admin builds for a `ModelAdmin` view. A wrapper defined in an installed app other than Django's own is that app's code unless its link leads into hosted code, judged past any bound method, partial or wrapper whose code is no app's, and past any other app's wrapper that is itself followed: the rule asks what the link serves as, recursively, so wrappers compose. A wrapper whose code is no app's only wraps and follows its `__wrapped__` wherever that leads: one Django supplies, in a contrib app (`login_required`, `permission_required`, `staff_member_required`) or in none (`never_cache`), and one in the project, so neither `login_required` nor a stack of project decorators changes which app a view serves as.
- **Wrappers** are followed to what they wrap, through the `__wrapped__` that `functools.wraps` leaves, read without running the author's code. An app's wrapper is followed only while its link leads into code of a hosted app, never into Django's or into code the view inherits; a wrapper whose code is no app's is always followed. An exact `functools.partial` runs no code of its own, so it is always its function's code, such as `functools.partial(sitemap, sitemaps=...)`, which is the sitemaps app's. A link to a class leads to the class's own module. A bound method is its function's code. An app's wrapper whose link is not followed counts as the code that runs, so a view wrapped that way in another app's module serves as that app (spec 02, after TRN-57), and the documentation says so.
- **`ModelAdmin` views.** Django wraps these so that their module is `django.contrib.admin.options` and marks them with `model_admin` (`ModelAdmin.get_urls`). The host takes the app of the most derived class in the MRO of `type(view_func.model_admin)` that is defined in a hosted app or in the project. When there is none, the classes are Django's (the stock `ModelAdmin`, `GroupAdmin`, the class `admin.site.register(Model, **options)` builds) or an app's with no declaration, and the host takes the model's app. That is the admin view's own app only: an app's wrapper over it is not followed, since its link leads into no hosted app's code. Options are configuration of the class Django builds and decide nothing. A class in the project gets no caller, and `neolith.W001` names it; the check and the binding use the one rule (`neolith._serving`). `neolith.W001` at set-up runs inside `ready()`, before any URLconf is imported, so it sees only the admin registrations made while the apps load; one made from the URLconf, or from a project module only the URLconf imports, is not warned about until a later run of the check, such as `manage.py check`.
- **Other views** take their function's module, and any other callable its type's module.
- **Views supplied by another installed app** (`django.contrib.auth`'s login view, the admin site's own views, a third-party app's views) run as that app.

**Binding.** The root middleware binds the app in `process_view`, through the root it keeps in a private variable while the request runs, whatever request object a middleware passes on, never through the host's variable, and sets the app and what it requires as one value, so a call made meanwhile in another thread reads both or neither. Django calls it after `resolve_request` and after every middleware's request phase. Because this middleware is outermost, its `process_view` runs before every other middleware's, so the rest of the request runs in the bound root: later `process_view`, `process_exception` and `process_template_response` methods and the response phase. A call made from another middleware's request phase, or on a request that never reaches a view, comes before binding.

**Principal and trace.** The trace identifier is generated when the root opens and is fixed from then on; an ordinary request's `traceparent` is not read. In a host with a principal backend, the root middleware's `process_view` hands a root it binds to an app the host holds the request and the backends set-up built from `NEOLITH["PRINCIPAL_BACKENDS"]` before it binds the root, in one step, so a call that sees the root bound, from any later `process_view` (the principal middleware's place in the list does not matter), a failure view or the body, resolves the root's one principal. A call made before binding, or from a root bound to no app the host holds, is refused at any time (spec 02, TRN-56 and TRN-58; TRN-39 for an app the host does not hold), so such a root gets no resolution: nothing is searched, marked or varied for it. The root's first call asks the backends in order (spec 05, A request's principal): the first principal decides, `None` abstains, and a raise or any other value is a failure, as is a call from the root made inside one of its own searches, by a backend or code it runs (it would otherwise search again or wait for itself), recorded on the root and logged with the trace identifier, after which every call from the root fails with `internal`. The root holds one outcome behind its own lock, which is never held across a search: a synchronous caller searches on its own thread, async callers on one event loop share one search in flight, and the first search to complete writes the outcome, which every later caller uses. No caller waits for another's search across sync and async, since a sync caller on the thread-sensitive thread would wait for a search that needs that thread. A search cut short by a cancellation records nothing.

The Django-user backend (`neolith.principals.DjangoUserBackend`) reads the request's user:
- When `request.user` is not a `SimpleLazyObject`, judged by `type()`, which a lazy object does not proxy, `login`, `logout`, `alogin`, `alogout` or other code such as Django REST framework's `Request.user` setter has put a plain instance there, and the backend uses it. This needs no I/O and is safe in the event loop.
- Otherwise it uses `request.user` from `resolve` and `await request.auser()` from `aresolve`. On Django 5.2, `auser()` keeps its own cache, which `alogout` does not clear; the type check above is what keeps a view that calls `alogout` and then resolves on the async path from calling on behalf of the user who just logged out.

The principal in force at the first call is the root's principal. A view that logs a user in or out after its first call keeps the old principal, and calls that must run as the new user open their own scope. A synchronous first call made directly in the event loop that reads the session there, which Django refuses, fails with `internal`; that failure is the root's outcome, so every later call from the root fails too, through `sync_to_async` as well. Async code makes its calls through `sync_to_async`.

**The latest point.** The principal middleware's response phase marks a root bound to an app the host holds, and no search starts after it. A call made later while no outcome is fixed, from the response phase of a middleware listed outside the principal middleware or from a thread that outlived the response, is a recorded failure and fails with `internal`, and a search still running then is dropped (spec 05, APP-59), so the host never reads the session where `SessionMiddleware` would no longer save what `get_user` changed (a `cycle_key` on a fallback key). Such code opens its own scope.

**Error and failure views.** Django calls `handler400`, `handler403`, `handler404`, `handler500` and `CSRF_FAILURE_VIEW` itself; `process_view` does not run for them. They run in the root as it stands:
- **unbound** when the error comes before `process_view`, which covers an unresolved URL (also the 404 that `APPEND_SLASH` and `LocaleMiddleware` turn into a redirect) and an exception in a request phase;
- **bound** when the error comes from the view or from a later `process_view` such as the CSRF check.

So an error view that calls a contract opens its own scope (ADR 0017 Decision 4).

**Closing.** How the root closes depends on the response:
- **Ordinary response.** The root middleware closes the root and resets the variable in a `finally` block when it returns, so a `BaseException` that escapes the chain also closes it, such as the `CancelledError` the ASGI handler raises on a client disconnect. `TemplateResponse` is rendered inside `_get_response`, before any middleware returns.
- **`FileResponse` over a plain file.** When `file_to_stream` is an `io.FileIO`, an `io.BufferedReader` over one, or an `io.BytesIO`, reading it runs no Python code. The response is left unwrapped, and its root closes when the middleware returns: replacing its `streaming_content` would clear `file_to_stream` (`FileResponse._set_streaming_content`), and `WSGIHandler` would then skip `wsgi.file_wrapper` and lose sendfile. Any other file-like object, such as a storage backend's file, may run code as it is read, so it is wrapped like any other body, and loses sendfile.
- **Any other streaming response.** Its body is iterated after the middleware returns, by the WSGI server or by the ASGI handler's `send_response`. The root middleware hands the root to a wrapper around `streaming_content`, which is a sync or async iterator object matching `response.is_async` and has a `close()` method, as `GZipMiddleware` wraps a body. An async generator would not work: Django registers a `close` attribute, and async generators lack one.
  - **Inside the root.** Each step sets the variable to the root around the item it pulls, so the body runs inside the root in whatever context the server iterates it.
  - **Normal close.** The wrapper takes over the closers Django registered for the body before it was wrapped (`_resource_closers`), such as a generator's `close`, so the body's own clean-up runs inside the root. It runs them, then closes the root, when the inner iterator is exhausted, raises, or is closed. Django registers the wrapper's `close()`, and `HttpResponseBase.close()` calls it, after the body on WSGI and after `send_response` on ASGI, including on a client disconnect during the send.
  - **An async body stopped early.** On a client disconnect the ASGI handler closes its own iterator over the body and the response, but never the body's async generator, which has no `close`. Its clean-up runs when the event loop finishes it, after the response is done, so a call from it is refused (spec 02, after TRN-61).
  - **Principal and `Vary`.** Before a streaming response that the root keeps is returned from a bound root whose principal is unresolved, the principal middleware's response phase resolves it, with `resolve` in sync mode and `aresolve` in async mode; a failure is only recorded. `SessionMiddleware` then sees the session access, adds `Vary: Cookie`, and saves any change `get_user` made to the session (`flush`, or `cycle_key` on a fallback hash). On every response whose root started a search, the principal middleware patches `Vary` with the union of the backends' request inputs, fixed at set-up (`authorization` and `cookie` for the Django-user backend), or `*`; a response whose root started none gains nothing. This is the per-request cost Decision 4 allows for streamed bodies, along with one context-variable set and reset per chunk.
  - **Late-close backstop.** A `weakref.finalize` on the wrapper closes the root when the wrapper is collected.
  - **Nothing a collection runs blocks on a lock.** A collection can run the wrapper's finalizer, or its `close()` through a dropped response's generator, while the thread holds the lock of the host's table of open scopes. Closing a scope takes no lock: it marks the scope closed, which refuses its calls, and the table entry goes the next time the lock is taken. App code a collection runs, such as a body's `finally` that makes a call, may open a scope, so the lock is re-entrant. A response dropped without being closed, as the test client's partly read stream can be, has its body finalized by the collector in whatever context the collection runs, as any Python finalizer is.
  - **A signal to stop from a closer** (`KeyboardInterrupt`, `SystemExit`) stops the closers after it and goes on with a note; the root closes whatever happens. One ASGI path needs it. For a streaming response with status 400 or above, `get_response_async` awaits `log_response` after the chain returns, and a client disconnect during that await cancels the request task before `send_response` starts. The handler then sends `request_finished` and never calls `response.close()`. The wrapper and the response always form a reference cycle, so the root closes at the next cyclic garbage collection that reaches it, with no fixed bound. Until then the body never runs, but an executor that inherited the root can still use it, and each call it makes is bounded only by its own deadline (spec 02).

**Sync and async views.** A sync view under ASGI runs through `sync_to_async`, and an async view under WSGI through `async_to_sync`. Both carry context variables across the switch. Thread-sensitive mode shares one thread, but each call runs in its own copy of the context, so roots do not leak between requests.

**Conformance cases for the Django host** (on WSGI and ASGI, with a sync and an async view): A connector call made from a `StreamingHttpResponse` body while the server iterates it succeeds, with both a sync and an async iterator; a call held over until after the response is closed fails; on ASGI, a client disconnect during a streamed body closes the root; on ASGI, a streaming 4xx response whose client disconnects before the body is sent has its root closed by the backstop once the wrapper is collected (the test forces a collection); a `FileResponse` keeps `file_to_stream`, and its root is closed when the middleware returns; and a call from another middleware's request phase, before `process_view`, is refused. The caller is tested too: an admin action registered in one app's `admin.py` calls a contract with that app as the caller, not `django.contrib.admin`; an admin action on a `ModelAdmin` subclass in a project-level module has no caller and is refused, and `neolith check` warns about it; a page that makes no connector call gets no `Vary` from the host and does not evaluate `request.user`, while a streamed body whose first connector call happens during iteration gets a `Vary` that names the backend's request inputs (`Cookie` and `Authorization` for the Django-user backend) and its principal resolved before the response is returned; an async view that calls `alogout` and then a contract calls with no principal, not as the user who logged out; two concurrent first calls share one principal and one trace identifier; a view from another installed app calls as that app; and an error view rendered for an unresolved URL has no caller.
